Sorting and searching form the beating heart of the algorithms work in AP Computer Science A. Other units in the course teach students to store values, move values, and transform values, yet this stretch of the syllabus is where stored values start behaving like a system. An array stops being a passive row of boxes and becomes a structure whose organization decides how quickly anything inside it can be found, ordered, or rearranged. Selection sort, insertion sort, and merge sort supply the course with its three sorting stories, while sequential search and binary search frame a contrast that echoes through all of computer science: the difference between looking everywhere and looking cleverly.

A stubborn misconception follows many students into this unit. Code for these algorithms is short, so the code looks memorizable, and a learner can recite a selection sort the way a song lyric gets recited, word perfect and understanding optional. The exam quietly punishes that approach. Questions seldom ask for the code itself; instead they show code in motion, freeze it halfway through a pass, swap two values, bend an index by one, and ask what the data holds now. Points flow to students who can trace, who can walk a procedure across a specific set of values and report the state of every variable at every step. Tracing, more than recall, is the skill this guide is built to train.

Everything that follows is organized around that skill. Each algorithm receives a careful hand trace on a small array, an honest count of the comparisons and moves it performs, and a close look at the mistakes its exam questions are designed to catch. A reference table gathers the whole unit onto one screen for fast review before a test. Readers who want the full course map first can begin with [the AP Computer Science A guide](/2008/07/05/ap-computer-science-a-guide/), which places this unit among the course's other major topics, and readers who meet unfamiliar vocabulary along the way will find pointers to the companion pieces that own those topics in depth.

## Where Sorting and Searching Sit in the Course and on the Exam

AP Computer Science A builds toward this unit from several directions at once. The arrays material teaches traversal, indexing, and the discipline of respecting a structure's bounds. The ArrayList material repeats those lessons inside a resizable container whose methods hide some mechanics and expose others. Recursion arrives as a way of thinking about problems that contain smaller copies of themselves. Sorting and searching sit at the crossing of those three roads, because a sort is a traversal with opinions, a search is a traversal with a goal, and merge sort is recursion wearing a practical disguise. Students who treated the earlier units as isolated chapters discover here that the course was quietly assembling one machine all along.

On the multiple-choice section, this material appears in several recognizable costumes. One costume is the frozen trace: a code segment runs partway, and the options describe possible states of the data, only one of which the algorithm could actually produce. Another costume is the counting question, where the stem asks how many comparisons, swaps, or iterations a run requires. A third costume is the modified code segment, where a loop bound shifts, a comparison operator flips, or an update line moves, and the question asks what changed. None of these costumes rewards a student who merely recognizes the algorithm's name. Each one rewards a student who simulates the algorithm honestly, step by step, without skipping the boring middle steps where errors hide.

Free-response questions ask for production rather than recognition. A typical prompt hands over an array or an ArrayList inside some class and asks for a method that searches it, sorts it, or rearranges it toward a stated goal. Graders read that code line by line, awarding points for correct traversal, correct comparisons, correct handling of boundary cases, and a correct return value. Sorting code written from shaky memory tends to fail in characteristic ways: a swap missing its temporary variable, a loop that stops one pass early, an inner index that restarts at zero instead of continuing from the outer index. Code written by a student who has traced the algorithm on paper dozens of times tends to survive, because the writer has already met those failure modes during practice and corrected them there.

Efficiency talk also belongs to this unit, though the course keeps it deliberately informal. Nobody on this exam derives a formal proof about growth rates. Instead, students learn to count operations, to compare counts as data grows, and to predict what doubling the input does to the workload of each procedure. That lens explains why binary search humiliates sequential search on large sorted data, why merge sort pulls away from the two simpler sorts as arrays grow, and why a programmer sorting a list once and searching it many times makes a different choice than a programmer searching an unsorted list exactly once. The counting habits built here reappear anywhere performance matters, which in real software is nearly everywhere.

Teachers often place this unit late in the course, after recursion, and the placement matters for study strategy. By the time sorting arrives, the exam is close enough that practice time competes with review time for every other unit. The efficient response is integration rather than isolation: trace sorting code as a way of reviewing loops, write a search method as a way of reviewing ArrayList handling, and let merge sort double as recursion review. A student who studies this unit that way is not adding a new subject so much as tightening bolts on subjects already learned, which is precisely why strong performance here often signals strong performance everywhere.

## The InsightCrunch Algorithms Reference

Exams reward students who can hold the whole unit in view at once, so this guide names its findable artifact the InsightCrunch algorithms reference: a single table that lines the five core procedures up side by side, with the trace signature of each one stated plainly. The trace signature column deserves special attention. It describes what a partially finished run looks like, and partial runs are what multiple-choice questions show. A student who can glance at a frozen array and name the algorithm and the pass that produced it owns a genuine scoring advantage.

| Algorithm | Core idea | Comparison growth as data grows | Extra memory | Trace signature partway through |
| --- | --- | --- | --- | --- |
| Selection sort | Repeatedly find the smallest remaining value and swap it into place | Quadratic, same count for every arrangement | None beyond a temporary variable | A sorted prefix of the smallest values sits at the front |
| Insertion sort | Slide each new value leftward into an already ordered prefix | Quadratic worst case, nearly linear on nearly ordered data | None beyond a variable holding the moving value | A sorted prefix sits at the front, but it holds the first values seen, not the smallest overall |
| Merge sort | Split the data in half, sort each half, then merge the halves | Grows as n log n in every case | A temporary structure for merging | Small ordered runs appear, doubling in length as merging proceeds |
| Sequential search | Inspect values one by one from the start until the target appears | Linear, half the data scanned on an average successful search | None | Only a scan position exists; the data itself never changes |
| Binary search | Probe the middle of the surviving interval and discard half of it | Logarithmic, one extra probe when data doubles | None for the iterative form | The data never changes; low and high markers close in on the target |

Reading the table vertically teaches the unit's geography. The first three rows reorder data and pay for that reordering with comparisons and moves. The last two rows leave data untouched and pay only for inspections. The middle column separates the procedures into growth families, and those families matter more than any exact count, because exam questions about efficiency almost always ask which family a run belongs to or what happens when the input doubles. Notice also the contrast hiding in the trace signatures of the two simple sorts. Both build a sorted prefix, which tempts beginners to treat them as twins, yet the prefixes contain different values at the same moment in a run, and that difference is a favorite exam trap that the selection and insertion sections below dismantle in detail.

Keep the reference nearby while working the traces that follow. After tracing an algorithm by hand, glance back at its row and confirm that the frozen states seen during the trace match the signature the table promises. That small verification loop, predict then check, converts passive reading into the active simulation skill the exam measures.

## The Array Skills Every Algorithm Stands On

Before any sorting happens, four humble operations deserve a hard look, because every algorithm in this unit is assembled from them. The first operation is indexed access: reading the value stored at a position, written with brackets in array code and with a get call on an ArrayList. The second operation is assignment into a position, which overwrites whatever sat there before, permanently and without apology. The third operation is traversal, the disciplined walk from index zero to the last valid index, which is always one less than the length. The fourth operation is comparison, asking whether one value is smaller, larger, or equal to another, which for numbers uses the ordinary relational operators and for objects uses a comparison method. Sorting is what happens when these four operations are arranged with intent.

Two of those operations hide traps that exam writers exploit relentlessly. Assignment destroys information: copying the value at one index into another index erases the second value unless something rescued it first. That single fact explains the most famous three lines in the unit, the swap. Traversal hides the second trap, the boundary: a loop that runs while its counter stays below the length visits every element exactly once, while a loop that allows the counter to equal the length reaches for an element that does not exist and throws an exception in real code or matches a wrong answer choice on the exam. Nearly every off-by-one error in sorting and searching is one of these two traps wearing a costume.

### Why does a swap need a temporary variable?

Assigning one element into another element's position erases the value that was sitting there, so a swap parks one value in a temporary variable first. The three statements copy the first value aside, overwrite its slot, then write the parked value into the second slot, exchanging both values safely.

Shifting deserves the same respect as swapping, because insertion sort is built from shifts rather than swaps. A shift copies a value one position to the right, deliberately overwriting the neighbor slot, and it only works because the value that was overwritten is safely held in a variable or was already copied onward. Shifting a whole run of values must proceed from the rightmost element leftward; shifting left-to-right through a run smears one value across every slot, a bug that produces eerily uniform arrays and zero sympathy from graders. Direction of movement is a recurring theme in this unit: searches move markers, insertion moves values, merge sort moves values between structures, and in every case the direction is dictated by which information would be destroyed by moving the other way.

ArrayList code repeats these lessons with method calls in place of bracket notation. Getting and setting take the place of reading and writing an index. Adding an element at an index shifts everything after it one position right at no charge to the programmer, which quietly removes the manual shifting burden, while removing an element shifts everything after it leftward. Searching an ArrayList still demands a traversal, and comparing its elements still demands a proper comparison method, since list elements are objects. The algorithms in this guide are presented on plain arrays for clarity, yet every one of them ports to an ArrayList with only mechanical changes, and exam questions move between the two containers freely, expecting students to notice that the logic survives the translation intact.

## Selection Sort, Pass by Pass

Selection sort grows from one clear idea: if the finished region must hold values in increasing order, then the next value placed there should be the smallest value still unplaced. The algorithm therefore divides the data into a sorted prefix on the left and an unsorted remainder on the right. Each pass scans the entire remainder, remembers the position of the smallest value found, and swaps that value into the first position of the remainder, which extends the sorted prefix by one. Passes continue until the remainder shrinks to a single value, and that last value needs no pass at all, because a lone remaining value is automatically the largest and already sits where it belongs.

The guarantee after each pass is crisp, and crispness is what makes this algorithm so traceable. After one pass, the smallest value in the whole collection sits at index zero, final and untouchable. After two passes, the two smallest values occupy the first two positions in order. Nothing in the remainder has been rearranged in any meaningful way; values there have only been looked at, plus the one value that got swapped away to the front. A frozen array showing a perfect sorted prefix of the smallest values, with chaos behind it, carries selection sort's signature, and recognizing that signature on sight is worth points.

Work through a complete run on the array 29, 10, 14, 37, 13, stored at indices zero through four. During the first pass, the scan begins with 29 as the smallest seen so far, then finds 10 smaller, keeps 10 against 14, keeps 10 against 37, and keeps 10 against 13, finishing with the minimum at index one. Swapping index one with index zero produces 10, 29, 14, 37, 13, and the 10 will never move again. During the second pass, the scan covers indices one through four: 29 leads briefly, 14 improves on it, 37 does not, and 13 improves on 14, so the minimum sits at index four. Swapping index four with index one gives 10, 13, 14, 37, 29, and now the prefix holds the two smallest values in order.

The third pass is the quiet one students most often misreport. Scanning indices two through four compares 14, 37, and 29, and the minimum turns out to be 14, already sitting at index two, the very position the pass is filling. The swap exchanges the value with itself and the array visibly does nothing: 10, 13, 14, 37, 29. Beginners frequently invent a change here, swapping 14 with 29 because 29 is smaller than 37, but the algorithm only ever compares against the running minimum, never against a neighbor. During the fourth pass, the scan of indices three and four finds 29 smaller than 37, the swap fires, and the array becomes 10, 13, 14, 29, 37. Four passes for five elements, exactly one fewer pass than the element count, and the procedure ends.

Pause on what the trace reveals about effort. Every pass compared the candidate against every value in the remainder, including comparisons that changed nothing, because selection sort has no way to know a value is the minimum until every rival has been checked. The first pass made four comparisons, the second made three, the third made two, and the fourth made one, for a total of ten comparisons on five elements. Swaps behaved completely differently: at most one swap per pass, and only three of the four passes swapped distinct values. Comparisons are this algorithm's currency, spent lavishly and predictably; swaps are rare and cheap. That asymmetry is the deepest fact about selection sort, and it explains both its exam behavior and its few real-world virtues.

### How many comparisons does selection sort make on an array of ten elements?

The first pass compares nine pairs, the next compares eight, and the counts shrink by one each pass until a single comparison remains. Adding nine, eight, seven, and the rest down to one gives forty-five comparisons, and that total never changes with the arrangement of the values.

Generalize that arithmetic and a formula appears. A run on n elements compares n minus one pairs on the first pass, n minus two on the second, and so on down to one, and that sum equals n times n minus one, divided by two. Growth like that earns the label quadratic: double the data and the comparison count roughly quadruples, since doubling n roughly quadruples the product. Feed selection sort one hundred values and it performs 4,950 comparisons; feed it one thousand values and the count climbs past 499,000. Notice something else, too: the count never depends on the arrangement of the values. Sorted data, reversed data, random data, all cost exactly the same comparisons, because the scan for a minimum cannot finish early. The algorithm is gloriously predictable, and exam counting questions lean on that predictability hard.

The code below is the standard form, and every line earns its place. The outer loop controls the boundary between the sorted prefix and the remainder. The inner loop performs the hunt for the minimum, carrying the position of the smallest value seen rather than the value itself, because the swap at the end needs to know where the minimum lives. Carrying a position instead of a value is a small decision with large consequences, and variants that carry the value and then guess its location are a classic source of broken student code.

```java
public static void selectionSort(int[] arr)
{
    for (int i = 0; i < arr.length - 1; i++)
    {
        int minIndex = i;
        for (int j = i + 1; j < arr.length; j++)
        {
            if (arr[j] < arr[minIndex])
            {
                minIndex = j;
            }
        }
        int temp = arr[i];
        arr[i] = arr[minIndex];
        arr[minIndex] = temp;
    }
}
```

Trace the code against the worked example and the correspondence clicks. When i is zero, the inner loop walks j from one to four, and minIndex settles on one, the home of the value 10. The swap places 10 at index zero and sends 29 to index one. When i is one, the inner loop walks j from two to four and minIndex ends at four, so 13 and 29 trade places. Two details deserve a second look. The inner loop starts at i plus one rather than zero, because positions before i are already sorted and final, and examining them again would waste comparisons and risk corrupting finished work. The swap happens once, outside and after the inner loop; moving the swap inside the inner loop is the single most common transcription error with this algorithm, and it produces a procedure that swaps eagerly every time a new minimum appears, still sorting correctly in many cases but doing far more swaps than the genuine algorithm, a difference counting questions can detect.

One more property rounds out the picture: selection sort is indifferent to its input in a way the other sorts are not. Because every pass scans the whole remainder, presorted input saves nothing, which makes the algorithm a poor choice for nearly ordered data. In exchange, its tiny swap count suits situations where moving data is expensive and comparing data is cheap, a niche the exam occasionally gestures at when it asks which sort minimizes writes. Understanding a sort means knowing its indifference as well as its enthusiasm, and selection sort is enthusiastic about exactly one thing: certainty. After each pass it knows, with proof, that its prefix is finished forever.

## Insertion Sort, Card by Card

Insertion sort borrows its logic from the way many people organize a hand of playing cards. Pick up one card at a time, and slide it leftward into the cards already held until it rests in its proper place among them. Translated into code, the algorithm again maintains a sorted prefix on the left, but the meaning of that prefix differs from selection sort in a way the exam probes constantly. Here the prefix holds the first several values of the original data, now arranged in order among themselves. Values in the prefix are not necessarily the smallest values overall, and positions in the prefix are not final, because the next inserted value may belong in the middle of the prefix and shove its residents one slot rightward.

### What is the sorted prefix that insertion sort builds?

Insertion sort treats the left edge of the array as a finished region that stays in increasing order. Each new value steps into that region from the right, shifting larger entries one slot over until a smaller entry or the array's edge stops it, and the region grows by one.

Trace it on the same starting data used for selection sort, the array 29, 10, 14, 37, 13, so the two runs can be compared honestly. The prefix begins as just 29, trivially in order. The value 10 steps up first: it compares against 29, finds 29 larger, shifts 29 one slot right, and settles at index zero, giving 10, 29, 14, 37, 13. Next the value 14 takes its turn: it passes 37 nowhere yet, since the turn begins at the boundary; it compares against 29, shifts 29 right, then compares against 10, which is smaller, so 14 stops at index one, producing 10, 14, 29, 37, 13. Already the contrast with selection sort glows. After two steps, selection sort had secured 10 and 13 in their final homes, while insertion sort has ordered the first three values seen and done nothing at all about 13.

The value 37 barely works. It compares against 29, its left neighbor at the boundary, finds itself larger, and stays exactly where it started; the array still reads 10, 14, 29, 37, 13. Then 13 makes the longest journey of the run. It compares against 37 and shifts it, compares against 29 and shifts it, compares against 14 and shifts it, and finally compares against 10, which stops the slide, so 13 lands at index one and the array finishes as 10, 13, 14, 29, 37. Same start, same finish, entirely different middle. Any exam question showing a frozen state from the middle of a run is asking whether the student knows which middles are legal for which algorithm.

Counting tells a subtler story here than it did for selection sort. The run just traced made eight comparisons in total: one for 10, two for 14, one for 37, and four for 13. Shifts numbered five. Both totals depend on the data. Hand insertion sort data that already arrives in order and every value stops after a single comparison against its left neighbor, giving n minus one comparisons and zero shifts for n values, a nearly linear performance that selection sort can never match. Hand it data in exact reverse order and every value slides the full width of the prefix, dragging the totals up to the same quadratic family as selection sort, with a heavy pile of shifts added. Insertion sort pays for what the data gives it: kind data, cheap run; cruel data, expensive run. That responsiveness, called adaptivity, is the algorithm's personality, and questions about best cases and worst cases are questions about this personality.

The standard code mirrors the card game closely. Each outer iteration lifts the boundary value into a variable, which frees its slot to receive a shifted neighbor, and then a while loop walks a second index leftward, copying values rightward for as long as they exceed the lifted value. When the walk stops, the lifted value drops into the vacated slot at the walker's right. Two guards keep the loop safe: the walker must still be inside the data, and the value it examines must actually be larger than the lifted value. Drop the first guard and a value smaller than everything before it sends the walker off the left edge; drop the second and the walk never stops at all.

```java
public static void insertionSort(int[] arr)
{
    for (int i = 1; i < arr.length; i++)
    {
        int value = arr[i];
        int j = i - 1;
        while (j >= 0 && arr[j] > value)
        {
            arr[j + 1] = arr[j];
            j--;
        }
        arr[j + 1] = value;
    }
}
```

Follow the code through the insertion of 13 in the worked example. The outer index i stands at four, value holds 13, and j starts at three, where 37 waits. Since 37 exceeds 13, 37 copies into index four and j falls to two. Since 29 exceeds 13, 29 copies into index three and j falls to one. Since 14 exceeds 13, 14 copies into index two and j falls to zero. Now the value at index zero is 10, which does not exceed 13, so the loop halts with j at zero, and the final assignment writes 13 into index one, exactly the slot the last shift emptied. Students who trace the j-plus-one landing spot correctly on paper almost never lose points on insertion code; students who write arr[j] instead donate them.

## Selection and Insertion Side by Side

Placed next to each other, the two simple sorts reveal themselves as different philosophies of patience. Selection sort does all of its hard work reading: it scans everything before daring to move anything, and it moves decisively once per pass. Insertion sort reads and writes constantly, nudging values around with nearly every comparison, but it reads only as much as each insertion requires. One algorithm's prefix is a trophy case, final and locked. The other's prefix is a waiting room, orderly but always ready to make space.

### Why do exam questions ask for the array after a single pass?

A pass snapshot exposes whether a student understands the algorithm's invariant, because each sort guarantees something different after one pass. Selection sort locks the smallest value at the front, insertion sort orders only a prefix, and a wrong choice among the options usually breaks one of those guarantees visibly.

Their counting profiles diverge just as sharply. Selection sort spends the same number of comparisons on every input of a given size and keeps swaps below the element count. Insertion sort lets comparisons and shifts float with the input's existing order, touching perfection on sorted data and drowning on reversed data. Questions that describe a scenario and ask for the wiser choice are testing precisely this divergence. Nearly ordered data arriving a piece at a time, like scores being entered into a leaderboard during an event, plays to insertion sort's strengths. A setting where writes are costly and comparisons cheap plays to selection sort's frugality with movement. Neither algorithm scales gracefully to enormous data, which is the opening through which merge sort enters the course.

## Merge Sort and the Power of Halving

Merge sort refuses to fight the whole array at once. It splits the data into two halves, sorts each half by the same splitting trick, and then merges the two sorted halves into one sorted whole. The splitting bottoms out at single elements, which need no sorting because a lone value is ordered by definition. Every real decision happens during merging, when two ordered runs are woven together by repeatedly taking the smaller of the two front values. Students meeting this algorithm for the first time often hunt for the moment where sorting happens and feel cheated when no such moment exists. Sorting here is an emergent property: trivially ordered pieces combine into larger ordered pieces, and order at scale assembles itself from order at small scale.

Recursion is the natural language for this idea, since the method that sorts a range calls itself on the left half and the right half before merging. The base case is a range of length one, or an empty range, returned untouched. The recursive case makes the two calls and then merges. Anyone shaky on base cases, call stacks, or the way a recursive method's local variables multiply across calls should detour through [the arrays and recursion guide](/2008/05/16/ap-computer-science-a-arrays-recursion/), which owns that machinery; this section borrows it and spends its budget on the splitting and merging behavior itself. What matters here is the shape of the work: a tree of calls, narrow at the top where one call owns everything, wide at the bottom where many calls own one element each, and merging effort flowing back up the tree.

Trace the algorithm on 8, 5, 9, 1, 7, 3, six values chosen so every merge has something to decide. The first split produces the left half 8, 5, 9 and the right half 1, 7, 3. Splitting the left half gives 8 alone and the pair 5, 9. Splitting the pair gives 5 and 9 as singles, which merge by comparing 5 against 9 and taking 5 first, rebuilding the ordered run 5, 9. Merging the single 8 with the run 5, 9 compares 8 against 5, takes 5, compares 8 against 9, takes 8, and then appends the leftover 9, yielding 5, 8, 9 for the left half. Nothing about the right half has been touched yet, which surprises students who expect the algorithm to work left to right through the original positions.

The right half now receives the same treatment. Splitting 1, 7, 3 gives the single 1 and the pair 7, 3. Splitting the pair gives 7 and 3, which merge into 3, 7, the only merge in the whole run where the right element wins the first comparison. Merging 1 with the run 3, 7 compares 1 against 3, takes 1, and then appends 3 and 7 in order, completing the right half as 1, 3, 7. The stage is set for the final merge between 5, 8, 9 and 1, 3, 7. Front values 5 and 1 compete, and 1 wins. Then 5 faces 3, and 3 wins. Then 5 faces 7, and 5 wins. Then 8 faces 7, and 7 wins. With the right run exhausted, 8 and 9 append in order. The finished sequence reads 1, 3, 5, 7, 8, 9, built from exactly five comparisons at the final level and a handful more below.

The merge step deserves its own magnifying glass, because it carries the entire algorithm. Merging two ordered runs uses two pointers, one at the front of each run, and repeatedly copies the smaller pointed value into the output, advancing that pointer. When one run empties, the entire remainder of the other run copies across without further comparisons, since those values are already ordered and all exceed everything placed so far. Every element moves exactly once per merge, and each comparison places at least one element, so merging runs totaling n elements costs at most n minus one comparisons and exactly n moves. A merge is linear work, tidy and predictable, and forgetting the leftover copy is the classic implementation bug: the sorted result silently loses the tail of the longer run.

Stack those linear merges into levels and the famous growth rate emerges. Six elements split into levels of runs: singles, then pairs and triples, then the whole. Each level of the tree processes every element once during its merges, so each level costs work proportional to n. The number of levels is the number of times n can be halved before reaching one, which grows as the logarithm of n. Multiplying levels by per-level cost gives the n log n family, dramatically gentler than quadratic. Double the data and the workload slightly more than doubles, one extra level applied to twice the elements, whereas a quadratic sort quadruples its workload for the same doubling. On a million values, merge sort performs on the order of twenty million comparison steps while a quadratic sort performs on the order of five hundred billion, a gap that separates seconds from hours.

Two honest costs balance the celebration. First, merging needs somewhere to put the woven output, so the algorithm consumes extra memory proportional to the data size, unlike the simple sorts that work entirely in place with a variable or two. Second, merge sort shows no adaptivity: already ordered data gets split and merged with the same effort as scrambled data, since the merge procedure cannot tell a gift from a challenge. Exam questions test both costs directly, asking which algorithm needs auxiliary space or which one keeps its runtime when the input arrives sorted. The algorithm also treats equal values gently, since a merge that prefers the left run on ties preserves the original relative order of equals, a property called stability that insertion sort shares and selection sort lacks. Stability rarely earns its own question, yet it explains several otherwise puzzling answer choices about records sorted twice by different keys.

Recognizing merge sort in a frozen trace takes a different eye than recognizing the simple sorts. No sorted prefix grows at the front. Instead, ordered runs of length two, then four, then eight appear across the data as merging levels complete, like seams stitching themselves longer. A multiple-choice stem showing the second half of the data ordered internally while the front remains untouched is showing a merge in progress, not a broken selection sort. Students who learn to see run structure, rather than prefix structure, stop falling for that particular distractor family.

## Sequential Search, the Honest Scan

Searching begins with the procedure every beginner invents independently: start at the beginning, look at each value in turn, and stop when the target appears or the data runs out. Sequential search, also called linear search, asks nothing of the data. The values may be sorted, reversed, scrambled, or freshly shuffled; the scan behaves identically, which is both its weakness and its great virtue. It returns the index of the first matching value, or negative one as the agreed signal that the target is absent. That negative one convention matters on the exam, where questions treat it as a meaningful answer rather than an error.

The code fits in a breath, and its simplicity makes it the perfect vehicle for teaching careful tracing. A loop carries an index from zero upward. Each iteration compares the value at that index against the target and returns the index immediately on a match. Falling out of the loop means every position failed the test, so the method returns negative one. Notice that the return inside the loop abandons the remaining iterations the moment success occurs, which is why a target sitting early costs so little. Notice also what the method refuses to do: it never returns a boolean dressed as an answer, never prints anything, and never assumes the target exists.

```java
public static int sequentialSearch(int[] arr, int target)
{
    for (int i = 0; i < arr.length; i++)
    {
        if (arr[i] == target)
        {
            return i;
        }
    }
    return -1;
}
```

Trace the scan on the unsorted array 29, 10, 14, 37, 13 with target 13. The comparisons march in order: 29 fails, 10 fails, 14 fails, 37 fails, and 13 succeeds at index four, costing five comparisons to search five values. Change the target to 20 and the same five comparisons occur, followed by the negative one verdict. Change the target to 29 and one comparison ends the search. Averaged over all possible targets in a successful search, the scan examines about half the data, which is why efficiency discussions describe its cost as linear in n: double the collection and the expected work doubles, no better and no worse. Questions that ask how many elements a sequential search examines in the worst case are fishing for the full length, and questions about the average case are fishing for half of it.

Sequential search also quietly wins several fights that flashier algorithms cannot enter. Data that arrives unsorted and will be searched exactly once should be scanned, never sorted first, because sorting costs far more than one scan. Data that changes constantly punishes any investment in maintaining order. Data stored in a structure without cheap random access in other languages and contexts often forces a walk anyway. The exam's scenario questions reward students who ask what the data's life looks like before reaching for the famous algorithm, and the honest scan is the right answer more often than pride suggests.

## Binary Search, Halving the Haystack

Binary search begins where sequential search's honesty becomes unaffordable. Given data in sorted order, there is no reason to inspect values one at a time from the edge, because a single well-chosen probe can eliminate half the collection. The algorithm maintains two markers, conventionally called low and high, that bracket the interval where the target could still hide. Each probe examines the midpoint of that interval. If the midpoint value equals the target, the search ends in triumph. If the target is larger, everything at and below the midpoint is innocent, so low jumps past the midpoint. If the target is smaller, high retreats to just below the midpoint. The interval halves, and halving, repeated, is devastatingly fast.

The sorted precondition is absolute, not a suggestion. Binary search draws its power from a promise: every value left of any position is no larger than the value there, and every value right of it is no smaller. The midpoint probe's verdict about which half to discard is only trustworthy because that promise holds. Run the same code on unsorted data and it executes without complaint, returning answers that mean nothing, sometimes finding the target by luck and sometimes discarding the very half that contains it. Exam questions exploit this by presenting binary search code alongside an unsorted array and asking what gets returned, and the only correct approach is to trace the code mechanically rather than reason about where the target ought to be.

### Why does binary search code compute the midpoint with integer division?

An index must name an actual slot, so the average of the low and high markers has to land on a whole number. Integer division discards the fractional part, rounding the midpoint down to a valid index, and that downward rounding still guarantees the search interval shrinks on every iteration.

Trace a successful search on the sorted array 3, 8, 12, 19, 25, 31, 42, 56, 67, 80, hunting for 42. Initially low is zero and high is nine, so the midpoint is index four, holding 25. Since 42 exceeds 25, the target can only live to the right, and low moves to five. The interval now spans indices five through nine, and the midpoint of five and nine is seven, holding 56. Since 42 is smaller than 56, high retreats to six. The interval spans indices five and six; the midpoint of five and six, computed with integer division, is five, holding 31. Since 42 exceeds 31, low advances to six. Low and high now agree on index six, the midpoint is six, and the value there is 42. Four probes searched ten values, and each probe's arithmetic is exactly the kind of detail a trace question examines.

An unsuccessful search is traced with equal care, because misses are where boundary errors breed. Hunt for 30 in that same array. The first probe, index four, finds 25, and since 30 is larger, low moves to five. The second probe, index seven, finds 56, and since 30 is smaller, high retreats to six. The third probe lands on index five, holding 31, and since 30 is smaller than 31, high retreats to four. Now low stands at five while high stands at four; the markers have crossed, the interval is empty, the target provably exists nowhere in the data, and the method returns negative one. Marker crossing is the termination signal, and code expresses it by looping while low stays less than or equal to high. Weakening that condition, or moving a marker to the midpoint itself instead of one past it, creates the infamous infinite loop in which an interval of one element probes itself forever.

```java
public static int binarySearch(int[] arr, int target)
{
    int low = 0;
    int high = arr.length - 1;
    while (low <= high)
    {
        int mid = (low + high) / 2;
        if (arr[mid] == target)
        {
            return mid;
        }
        else if (arr[mid] < target)
        {
            low = mid + 1;
        }
        else
        {
            high = mid - 1;
        }
    }
    return -1;
}
```

Read the code for the decisions it encodes. High starts at the last valid index, not at the length, a one-word difference between a working method and an exception. Both marker updates step one position beyond the midpoint, because the midpoint value has been examined and acquitted; leaving a marker on the midpoint invites the loop to probe the same element repeatedly. Equality gets tested before the directional branches, so a lucky first probe ends the search immediately. The whole method is a small masterpiece of boundaries, which is why this algorithm generates more off-by-one exam questions than everything else in the unit combined.

The payoff for that care is the most dramatic counting story in the course. Ten values needed at most four probes. One thousand sorted values need at most ten probes, since halving a thousand reaches a single value in ten steps. A million values need at most twenty. Doubling the data costs exactly one additional probe, the defining signature of logarithmic growth, and it is why sorted structure is worth maintaining in real systems that search constantly: the haystack can grow a thousandfold while the search grows by ten looks. Set beside sequential search's million inspections on the same data, binary search's twenty probes explain why this unit treats sorting and searching as partners rather than strangers. Sorting is the investment; searching is where the returns get collected.

## Tracing Like a Grader

Tracing is a performance skill, and like every performance skill it improves under a system. The system that works under exam pressure is embarrassingly physical: draw the array as a row of boxes on scratch paper, write indices above the boxes, and record every variable that matters beneath the boxes in columns, one row per step. When a loop iterates, a new row begins. When a value moves, cross out the old entry and write the new one rather than erasing, because the crossed-out history is often what a follow-up part of the question asks about. Students resist this bookkeeping because it feels slow, yet it converts a juggling act into a lookup, and under time pressure the lookup wins every time.

A state table for a sort tracks a predictable cast: the outer index, the inner index, the position of the current minimum or the value being inserted, and the array's contents. For a search, the cast shrinks to low, high, mid, and the value found at mid. Writing the array's contents after every pass, rather than after every microscopic step, balances completeness against speed for sorting questions; writing them after every probe is cheap enough for searches. The discipline is to update the table at the same rhythm the question uses, and exam questions telegraph their rhythm: options that show array states correspond to pass boundaries, while options that show index values correspond to individual iterations.

Distractor design follows a small grammar that students can learn to read. Wrong answers on trace questions are rarely random; they are the outputs of plausible buggy algorithms. One option is usually the state produced by the other simple sort, catching students who traced the wrong procedure. One option is the correct algorithm arrested one pass too early or pushed one pass too far. One option swaps the roles of two indices, producing a state where the right multiset of values stands in subtly wrong positions. One option shows the result of comparing with a neighbor instead of a running minimum, or of shifting in the wrong direction. Naming each distractor's bug as it gets eliminated turns a guessing exercise into an audit, and audits are faster and more reliable than intuition.

Code-segment questions add one more wrinkle: the code shown may not be the canonical algorithm at all. A loop bound might exclude the final element, a comparison might be strictly greater where greater-or-equal belongs, or the swap might fire inside the inner loop. The winning habit is to trace the code as written, not the algorithm as remembered. That instruction sounds trivial and is violated constantly, because memory is fluent and tracing is effortful, and under pressure the brain prefers fluency. Graders and question writers both know this. Free-response graders award points for the code the student actually wrote behaving correctly; multiple-choice writers plant options matching the canonical algorithm's output precisely to catch students who answered from recognition rather than simulation. Tracing the artifact in front of the eyes, never the ideal in the head, is the unit's golden rule.

Speed arrives as a byproduct of structure rather than a substitute for it. A student who has traced fifty runs on paper develops compression instincts: selection sort passes get summarized by where the minimum landed, binary search probes get summarized by interval endpoints, and whole passes collapse into single table rows. That compression is earned fluency, and it differs from the beginner's shortcut of skipping steps in one crucial way: the fluent tracer can always decompress on demand when an answer looks wrong. Practice therefore works best in two gears, slow full traces while learning an algorithm, then rapid summarized traces once the mechanics are reliable, with a return to slow gear whenever an error appears. Errors are diagnostic gold; each one names a specific misunderstanding that can be repaired before the exam charges tuition for it.

## Efficiency Without Tears: Counting What Algorithms Do

Efficiency questions frighten students who believe they require mathematics beyond the course, yet the exam's version of the topic is friendly arithmetic wearing a trench coat. The core move is counting: how many comparisons does this run perform, how many swaps, how many iterations, and how do those counts change when the data doubles? Every efficiency idea in this unit is built from that move. A comparison is the atomic unit of sorting work because ordering information enters the algorithm only through comparisons. A swap or a shift is the atomic unit of movement. Counting both, separately, explains profiles that a single vague notion of speed would blur, like selection sort's mountain of comparisons beside its molehill of swaps.

Growth families organize the counts into a story students can carry anywhere. Linear growth means the count tracks the data size: double the data, double the work, as with a sequential search. Quadratic growth means the count tracks the square of the size: double the data, quadruple the work, as with the comparison counts of the two simple sorts. The n log n family sits between, governing merge sort: double the data and the work a bit more than doubles. Logarithmic growth is the aristocrat: double the data and the work grows by a single step, as with binary search probes. Exam questions rarely demand the family names; they demand the doubling predictions, which are the same knowledge with the vocabulary stripped away.

Consider the doubling experiment concretely, on data growing from one thousand elements to two thousand. Sequential search roughly doubles its average inspections, from about five hundred to about one thousand. Selection sort roughly quadruples its comparisons, from about half a million to about two million. Merge sort climbs from about ten thousand comparison steps to about twenty-two thousand, a shade worse than doubling because the taller tree adds a level. Binary search adds exactly one probe, moving from ten to eleven. Spread across one table of results, those four behaviors explain nearly every efficiency answer the course expects, and each behavior traces back to a mechanism already traced by hand in this guide: the scan, the full rescan per pass, the halving split, the halving interval.

Counting questions have their own micro-genre conventions. A stem that asks how many times a particular line executes usually wants loop arithmetic, multiplying an outer count by an inner count and adjusting for bounds that shrink. A stem asking which algorithm performs a stated number of comparisons on given data wants the counts run backward into an identification, where selection sort's arrangement-independent total betrays it instantly and insertion sort's total must be reasoned about from the data's existing order. Students who practice counts in both directions, forward from code and backward from totals, find these questions deflate from intimidating to clerical.

A caution keeps the whole topic honest: the course counts operations, not seconds. Wall-clock time depends on hardware, language details, and a hundred accidents that no exam can standardize, so questions speak in comparisons, swaps, iterations, and probes. That convention is a gift to students, because operation counts live entirely inside the code and the data, both printed on the page. Nothing needs measuring in a laboratory; everything needs simulating on paper. Efficiency, in this course, is tracing with a tally sheet, which is one more reason the tracing habit carries the whole unit.

## Choosing the Right Algorithm Under Exam Pressure

Scenario questions convert all of this knowledge into judgment. They describe a dataset and a task, sometimes with a constraint tucked into the wording like a splinter, and ask which procedure fits. The splinter is always the point. Data described as already sorted, or nearly sorted, points at insertion sort among the sorts and makes binary search legal among the searches. Data described as enormous points at merge sort. Data described as unsorted and searched a single time points at sequential search with a confidence that surprises students who equate famous with appropriate. The reading skill matters as much as the algorithm knowledge: underline the properties the stem grants the data, because the correct choice is the one whose preconditions and strengths match those properties exactly.

The most instructive scenario in the unit combines both halves. Suppose a program must answer many searches against a collection that never changes. Searching sequentially each time pays the linear toll on every query, while sorting once and searching with binary probes pays a single sorting toll and then charges almost nothing per query. Somewhere a break-even number of queries exists: below it, lazy scanning wins; above it, the sorted investment wins easily. Exam versions of this scenario keep the numbers small and the reasoning qualitative, yet the underlying trade is the same one real systems make when they build an index. A related scenario hands over a nearly sorted collection needing occasional insertions, where insertion sort's adaptivity quietly beats merge sort's indifference, and another hands over records already sorted by one key that must be re-sorted by a second key, where a stable sort preserves the earlier ordering inside ties, the one corner where stability stops being trivia.

Choices also hide inside code-writing prompts. A free-response part that says values are in no particular order and asks whether a target exists is licensing sequential search; the same prompt with a sentence guaranteeing sorted order is begging for binary search, and a student who scans anyway may still earn correctness points while hemorrhaging time and elegance, and may lose points if the rubric specifies behavior. A prompt asking for the kth smallest value whispers selection sort's invariant, since k passes of selection leave the k smallest values parked at the front. Reading prompts for the algorithm they imply is a learnable reflex, and it begins with the same question every time: what does the stem promise about the data?

When no promise appears, defensive choices rule. Assume nothing about order unless stated. Assume the target might be absent and handle the miss. Assume the collection might be empty and make the code survive it gracefully, which for every algorithm in this unit means loops that simply never execute and searches that fall through to negative one. Edge cases are not pedantry; they are where scenario questions and free-response rubrics concentrate their traps, because professional code meets edge cases daily and the course wants students thinking like professionals in miniature.

## Sorting Words and Objects: When compareTo Enters

Numbers sort themselves with the familiar relational operators, but the exam's data quickly grows past numbers. Strings order themselves alphabetically through compareTo, a method that returns a negative value when the calling string belongs before the argument, zero when the two are equal in content, and a positive value when the caller belongs after. Every comparison inside the sorts adapts by replacing an operator with that method's sign. Where numeric code asks whether one value is smaller than another, string code asks whether a compareTo result is negative. The algorithms themselves do not change at all, which is itself a tested insight: sorting is a pattern of comparisons and moves, indifferent to what the comparisons examine.

Objects raise the stakes further. A student class with names and grade point averages has no natural operator ordering, so the class or the sorting code must define ordering through compareTo from the Comparable interface, comparing by one field or by a chain of fields when ties occur. Searching object collections adds a second subtlety: locating an object by identity, the very same object in memory, differs from locating an object by content, an equal-valued twin. The equals method defines content equality, while the double-equals operator compares references. ArrayList searching methods lean on equals, and a class that fails to override equals inherits a version that behaves like reference comparison, a trap that has embarrassed real programmers and exam candidates alike. Students who want the full object-oriented picture, including how these methods get written and tested under free-response conditions, will find it in [the OOP and FRQ guide](/2008/06/30/ap-computer-science-a-oop-frq/); this section needs only the comparison mechanics themselves.

A miniature example binds the ideas together. Imagine a roster stored as an ArrayList of strings: Priya, Marcus, Elena, Tom, Aisha. Sorting it with insertion logic compares Marcus against Priya and, finding Marcus earlier alphabetically, shifts Priya right and inserts Marcus at the front. Elena then slides past Priya and Marcus to the front, since E precedes M and P. Tom compares against Priya, the largest entry in the prefix, and stays exactly where it is. Aisha slides past everyone to index zero. The final order reads Aisha, Elena, Marcus, Priya, Tom, produced by exactly the shifting machinery from the numeric trace, with compareTo playing the role the less-than operator played before. Searching the sorted roster for Marcus with binary logic probes index two first, and since Marcus happens to sit in that exact middle slot, the search ends after a single probe.

One difference between arrays and ArrayLists genuinely matters here. Inserting into the middle of an ArrayList through its add method shifts the tail automatically, while insertion sort on a raw array performs those shifts by hand in its inner loop. Students sometimes conclude that the list version must be faster, but the shifts still happen; they merely occur inside the method rather than inside student code, and counting questions count them either way. The container changed; the work did not. That sentence generalizes across the entire unit and might be its most portable lesson: algorithms describe work, containers describe storage, and exam questions that swap containers while keeping algorithms constant are testing whether the student can tell the two apart.

## A Free-Response Merge, Worked in Full

Abstract advice about free-response questions only goes so far, so consider a complete specimen in the style the exam favors. A prompt presents two ArrayLists of integers, each guaranteed to be in increasing order, and asks for a method that returns a new ArrayList containing every value from both lists, still in increasing order. No sorting may be called, and the original lists must survive unmodified. The prompt is merge sort's beating heart removed from the recursion and asked to stand alone, and it tests traversal, comparison, and leftover handling in one compact package.

The plan writes itself once the merge step from earlier in this guide is recognized. Two indices walk the two lists, one per list, and each step compares the two values under the indices, appends the smaller to the result, and advances the index that supplied it. When one list empties, the other list's remaining values are all larger than everything placed and already ordered among themselves, so they append in a simple drain loop. Returning the freshly built list satisfies the requirement that the inputs stay untouched, since nothing ever wrote into them.

```java
public static ArrayList<Integer> mergeRuns(ArrayList<Integer> a, ArrayList<Integer> b)
{
    ArrayList<Integer> result = new ArrayList<Integer>();
    int i = 0;
    int j = 0;
    while (i < a.size() && j < b.size())
    {
        if (a.get(i) <= b.get(j))
        {
            result.add(a.get(i));
            i++;
        }
        else
        {
            result.add(b.get(j));
            j++;
        }
    }
    while (i < a.size())
    {
        result.add(a.get(i));
        i++;
    }
    while (j < b.size())
    {
        result.add(b.get(j));
        j++;
    }
    return result;
}
```

Trace the method on the lists 2, 9, 14 and 5, 7, 20. The opening comparison weighs 2 against 5, takes 2, and advances the first index. Then 9 faces 5, so 5 joins the result, and 7 follows when 9 faces it next. The comparison after that weighs 9 against 20 and takes 9, then 14 against 20 and takes 14, at which point the first list is empty and the main loop ends. The second drain loop never stirs, while the third appends 20, completing the result 2, 5, 7, 9, 14, 20. Five comparisons did all the deciding, matching the merge cost predicted earlier: at most the combined size minus one.

Graders read such a method hunting for specific landmarks: both indices initialized, the loop guarded by both lists having elements left, the comparison pointing the right way, exactly one index advancing per step, both leftovers drained, and the new list returned. The two classic point-losers live at predictable addresses. Forgetting the drain loops truncates the answer whenever one list outlasts the other, which is nearly always. Advancing both indices after a comparison discards an unexamined value and corrupts the count. A subtler choice hides in the comparison operator: taking from the first list when values tie, as the less-than-or-equal sign does here, preserves the first list's copies ahead of identical values from the second list, the stability habit from the merge sort discussion, and rubrics smile on it even when they do not demand it.

Writing this method in an exam booklet takes minutes, yet it draws on the entire unit: traversal discipline, boundary respect, comparison fluency, and the leftover insight that merging teaches. That density is typical of the course's free-response design, and it explains the study strategy the next sections press. Skills compound, so practice should compound too, mixing algorithms inside single problems rather than drilling each in a sealed compartment.

## The Mistakes That Cost Points

Certain errors recur so faithfully in this unit that they deserve a rogues' gallery. The most prolific offender is the off-by-one error, which breeds wherever an index meets a boundary. Loops that run to the length instead of one short of it reach for a phantom element. Searches that set the high marker to the length import the same phantom into binary search. Pass counts that run n times instead of n minus one add a phantom pass in which nothing can change. Each variant is the same misunderstanding wearing new clothes: the last legal index of a structure with n elements is n minus one, and the count of boundaries inside n elements is different from the count of elements. Students who chant that distinction while tracing catch these errors in the wild.

The swap family of errors comes next. Writing two assignments without the temporary variable destroys one value and duplicates the other, producing data with a repeated element and a missing one, an outcome so distinctive that graders recognize it instantly. Swapping inside the inner loop of selection sort inflates the swap count and betrays itself to counting questions. Swapping values when the code holds indices, or indices when the code holds values, scrambles the algorithm's bookkeeping mid-run. Every swap error shares a root: the writer stopped picturing what each variable physically holds. The cure is the trace table, where a variable's contents are written down and therefore cannot be wished into something else.

Binary search contributes its own beloved failures. Updating a marker to the midpoint rather than one past it can strand the loop on a single element forever. Computing the midpoint from stale markers after an update sends probes backward into territory already cleared. Running the algorithm on unsorted data and trusting the verdict confuses mechanical execution with meaningful answers. The subtlest failure is concluding that a missed target means an error occurred, when the negative one return is the algorithm's correct, designed response to absence. Questions probe each of these deliberately, and each yields to the same defense: trace the markers, in writing, one probe per row.

Insertion sort's signature disasters involve direction. Shifting a run of values in the wrong direction smears one value across the prefix, overwriting entries that were never copied anywhere safe. Guarding the inner while loop with the conditions in the wrong spirit, or omitting the boundary guard, lets the walking index escape below zero whenever a small value travels the full width of the prefix. Misplacing the final assignment by one index, writing into the walker's slot rather than the slot beside it, quietly overwrites a value that earned its place. Merge sort answers with two disasters of its own: dropping the leftover drain, and recursing without a base case that actually triggers, which in real code ends in a stack overflow and on paper ends in a trace that never terminates. Read the gallery again and notice the pattern: not one of these errors is exotic. All of them are small, mechanical, and mercilessly hunted by question writers, which means all of them are preventable by small, mechanical, merciless tracing.

## A Second Look at Insertion Sort: Duplicates Change the Story

Real data contains duplicates, and duplicates interrogate an algorithm's comparison operators in ways clean data never does. Run insertion sort on 5, 2, 5, 1, 4, where the value 5 appears twice. The prefix opens with the first 5 standing alone. The value 2 compares against 5, finds it larger, shifts it right, and takes index zero, producing 2, 5, 5, 1, 4. Now the second 5, sitting at index two, takes its turn. It compares against the first 5 at index one, and here the operator decides everything: the shifting condition asks whether the prefix value is strictly greater than the moving value, and 5 is not strictly greater than 5, so the walk stops instantly and the second 5 remains at index two. The array is unchanged by that turn, 2, 5, 5, 1, 4, and the two equal values have kept their original left-to-right order.

Keep tracing. The value 1 compares against 5 and shifts it, compares against the other 5 and shifts it, compares against 2 and shifts it, then reaches the front edge and lands at index zero: 1, 2, 5, 5, 4. The value 4 compares against 5 and shifts it, compares against the second 5 and shifts it, then compares against 2, which stops the walk, so 4 settles at index two and the run finishes as 1, 2, 4, 5, 5. Eight comparisons and six shifts did the work. Change the shifting condition to greater-than-or-equal and the trace diverges: the second 5 would shift the first 5 rightward and pass it, reversing the equal pair's order. On plain integers the reversal is invisible, since the values are identical. On records, where each 5 might be a student with a name attached and the first 5 arrived earlier, the reversal scrambles arrival order, and the sort has quietly stopped being stable.

Stability, introduced during the merge sort discussion, turns out to be decided by exactly these operator choices. Insertion sort with a strict comparison is stable because a moving value never crosses an equal value. Selection sort is not stable in its standard form, because a swap can hurl a value across its equal twin in a single motion: picture 5a, 5b, 3, where swapping the minimum 3 with the front element throws 5a behind 5b. Merge sort with a merge that prefers the left run on ties stays stable. Exam questions about pure numbers ignore all of this, but questions about records sorted by one key and then another depend on it entirely, and students who understand the operator-level cause can reason through such questions instead of guessing.

Duplicates stress the searches differently. Sequential search returns the first match and stops, which raises a question the exam does ask: what if a task needs every occurrence, or the last one? The scan adapts by continuing after a match and remembering the most recent index, at the price of always examining the whole collection. Binary search on data with duplicates returns whichever copy the probes happen to land on, with no promise about first or last, and its returned index can shift if the array's size changes the midpoint path. A student who expects binary search to find the first occurrence, the way a careful scan does, will miss questions built on exactly that expectation gap.

## Degenerate Inputs: Empty, Single, Equal, Sorted, Reversed

Algorithms reveal their construction when the data stops cooperating, so walk the five procedures across five hostile inputs. Begin with the empty array, a structure with length zero. Every sorting loop in this guide simply never executes: selection sort's outer loop demands an index below negative one, insertion sort's outer loop starts at one and finds nothing to start on, and merge sort's base case swallows the emptiness immediately. Sequential search falls through its loop and returns negative one, the only honest answer. Binary search opens with low at zero and high at negative one, its loop condition fails before any probe, and negative one emerges again. Empty data is not a special case bolted onto these algorithms; correct boundary choices make emptiness boring, and boring is the goal.

A single element behaves almost as quietly. Sorts leave it untouched, searches either find it with one comparison or dismiss it with one comparison, and binary search performs exactly one probe at index zero. An array of all equal values, say six copies of 7, is more talkative. Selection sort scans and swaps values with themselves, spending its full fifteen comparisons on six elements to accomplish nothing visible. Insertion sort stops each insertion after one comparison, because nothing in the prefix is strictly greater than the moving 7, finishing with five comparisons total and zero shifts, its best-case behavior triggered by equality rather than by order. Binary search finds a 7 at its first probe, the midpoint, and returns that middle index, which surprises students expecting index zero and teaches the durable lesson that searching promises a match, not the first match.

Sorted input separates the personalities with theatrical clarity. Insertion sort glides, paying one comparison per element and never shifting. Selection sort pays full price anyway, constitutionally incapable of noticing the gift. Merge sort also pays full price, splitting and merging with undiminished effort, its levels indifferent to the order they reassemble. Reversed input flips the comedy. Insertion sort suffers its worst case on every insertion, selection sort still pays exactly the same as always, and merge sort still pays exactly the same as always. Two algorithms in this unit have moods, and three have metronomes, and nearly every scenario question ever written about input shapes is asking the student to tell moods from metronomes.

Reversed input also furnishes the cleanest counting exercise in the unit. Insertion sort on five reversed values, 5, 4, 3, 2, 1, inserts 4 after one comparison and one shift, inserts 3 after two comparisons and two shifts, and continues the pattern through 1, which demands four comparisons and four shifts, for totals of ten comparisons and ten shifts. Five sorted values demanded four comparisons and no shifts at all. Same algorithm, same size, wildly different bills, and the difference lives entirely in the data. Students who can produce both bills from first principles own the concept of input-sensitive cost, which is the seed from which all serious algorithm analysis grows.

## The Invariant: Every Algorithm Keeps a Promise

Underneath the traces and counts sits one idea that organizes the whole unit, usually taught implicitly and worth naming outright. An invariant is a statement about the data that an algorithm guarantees stays true at a chosen checkpoint, typically the top of each loop iteration. Selection sort's invariant declares that the prefix before the outer index holds the smallest values, in final order, and will never be touched again. Insertion sort's invariant declares that the prefix holds the values it started with, in order among themselves, with no promise about finality. Binary search's invariant declares that if the target exists anywhere, it exists between low and high inclusive. Merge sort's invariant, applied at each merge, declares that two ordered runs enter and one ordered run leaves.

Invariants are not decoration; they are debugging instruments. When a trace goes wrong, the invariant names the exact moment of betrayal, because the first state that violates the promise is the first state produced by the buggy step. A student checking selection output after pass two who finds a value smaller than the prefix maximum still sitting in the remainder knows the minimum hunt failed, not the swap, because the swap only moves what the hunt selected. A binary search whose interval excludes an unchecked region containing the target has broken its promise at the marker update, and the invariant points at that update like a witness pointing at a suspect.

Exam questions test invariants constantly while almost never using the word. A question showing a frozen array and asking which algorithm could have produced it is asking which invariant the frozen state satisfies. A question asking what must be true after k passes of selection sort is asking for the invariant with k substituted in. A question asking where a target can still hide after several binary search probes is asking for the interval the invariant protects. Teaching the hand to trace is the mechanics; teaching the eye to check promises is the mastery, and the two skills reinforce each other every time a student verifies a trace.

Writing code benefits from invariants just as directly as tracing does. A programmer who states the invariant before writing the loop knows precisely what the loop must restore at the end of each iteration, and the code's structure falls out of that requirement. The minimum hunt exists to restore selection's promise after the boundary advances. The shifting walk exists to restore insertion's promise after a new value joins the prefix. The marker updates exist to restore the search's promise after a probe eliminates half the interval. Students who write loops by restoring promises make fewer boundary errors than students who write loops by imitating shapes, because every line has a job description and a line without a job gets noticed.

## Binary Search, Recursively

Binary search wears recursion as naturally as merge sort does, and the course's recursion material often introduces the algorithm in that costume before the iterative version appears. The recursive formulation takes the array, the target, and the two markers as parameters. A call first asks whether the interval has collapsed: if low exceeds high, the target is absent and the call returns negative one, which is the base case. Otherwise the call computes the midpoint, checks for a match, and ends with a single recursive call on the surviving half, returning whatever that call returns. Each call handles one probe and delegates the rest, so the chain of calls mirrors the sequence of probes exactly, one stack frame per halving.

Trace the recursive version hunting for 42 in the familiar array 3, 8, 12, 19, 25, 31, 42, 56, 67, 80. The opening call owns the interval zero through nine, probes index four, finds 25, and recurses on five through nine. That call probes index seven, finds 56, and recurses on five through six. The next call probes index five, finds 31, and recurses on six through six. The final call probes index six, finds 42, and returns six, which each waiting call passes upward untouched until the original caller receives it. Four calls, four probes, and the correspondence between the recursion tree here and the split tree in merge sort is no accident: both algorithms spend their effort by halving, and halving is recursion's home turf.

Choosing between the two forms on the exam is mostly a matter of reading which form the question presents. Iterative questions test marker arithmetic inside a loop; recursive questions test base cases, parameter passing, and the discipline of returning the recursive call's result rather than discarding it and continuing to loop or probe locally, a classic bug pattern in student-written recursive searches. A recursive search that forgets to return its recursive call can wander back into code after the delegation and overwrite the correct answer, and trace questions plant exactly that flaw.

Reading recursive code fluently pays rent across the whole back half of the course, and this algorithm is the gentlest place to build that fluency because its recursion is linear rather than branching: each call spawns at most one child, unlike merge sort's two children per call. Students who master the single-file line of calls here find merge sort's branching tree far less forbidding afterward. The study order practically suggests itself: trace iterative binary search until the markers feel inevitable, then trace the recursive form until the base case feels inevitable, and let the pair of them anchor the halving idea that the entire unit keeps reusing.

## Merge Sort on Eight Elements, Level by Level

One more merge trace, larger than the first, cements the run-reading skill. Take the array 14, 3, 27, 8, 19, 6, 22, 11. Splitting halves it into 14, 3, 27, 8 and 19, 6, 22, 11, halves those into pairs, and halves the pairs into singles, though the merges begin rebuilding before the mind needs to picture every split. At the lowest merge level, pairs combine: 14 and 3 become 3, 14; 27 and 8 become 8, 27; 19 and 6 become 6, 19; 22 and 11 become 11, 22. Each of those merges costs exactly one comparison, and the array of runs now reads 3, 14, 8, 27, 6, 19, 11, 22 when the runs are laid end to end.

The next level merges runs of two into runs of four. Weaving 3, 14 with 8, 27 compares 3 against 8 and takes 3, compares 14 against 8 and takes 8, compares 14 against 27 and takes 14, then appends the leftover 27, yielding 3, 8, 14, 27 in three comparisons. Weaving 6, 19 with 11, 22 compares 6 against 11 and takes 6, compares 19 against 11 and takes 11, compares 19 against 22 and takes 19, then appends 22, yielding 6, 11, 19, 22, also in three comparisons. The end-to-end picture now reads 3, 8, 14, 27, 6, 11, 19, 22: two immaculate runs of four, with disorder surviving only at the seam between them.

The final merge attacks that seam. Comparing front values 3 and 6 takes 3. Comparing 8 and 6 takes 6. Comparing 8 and 11 takes 8. Comparing 14 and 11 takes 11. Comparing 14 and 19 takes 14. Comparing 27 and 19 takes 19. Comparing 27 and 22 takes 22. With the right run exhausted, 27 appends without a fight, and the result stands as 3, 6, 8, 11, 14, 19, 22, 27. Seven comparisons settled the top level, one fewer than the eight elements merged, matching the merge budget exactly. Total comparisons across all levels: four at the pair level, six at the run-of-four level, seven at the top, seventeen in all for eight elements, comfortably inside the n log n envelope, which for eight elements budgets three levels of at most eight placements each.

Set this trace beside the selection trace on five elements and the philosophical difference sharpens. Selection sort's intermediate states are globally lopsided: perfection at the front, anarchy behind. Merge sort's intermediate states are locally perfect and globally seamed: order exists everywhere, but only within run boundaries that keep doubling. A scrambled-looking array whose halves are each internally ordered is not unsorted work waiting to happen; under merge sort it is work nearly finished. Exam questions that display such states are testing whether the student's eye has learned the second pattern, and students fresh from this trace tend to spot it instantly, the way a reader spots a familiar word in a paragraph of strangers.

## Variations the Exam Loves: Descending Order and Partial Jobs

Once the standard algorithms are traced comfortably, exam writers reach for variations, and each variation tests whether understanding or habit is doing the driving. The gentlest variation flips the goal: sort into decreasing order instead of increasing. Nothing structural changes. Selection sort hunts the maximum instead of the minimum, or equivalently keeps the minimum hunt and fills the array from the back. Insertion sort shifts while prefix values are smaller than the moving value rather than larger. Binary search on decreasing data reverses its verdicts, moving low when the midpoint is larger than the target and high when the midpoint is smaller. Students with genuine understanding adjust the comparisons and trace on calmly; students running on habit produce ascending results and pick the confidently wrong option.

A second beloved variation asks for partial work. Finding the largest value in unsorted data is one pass of a selection-style scan with no swap at all. Finding the three largest values is three passes of selection sort, full stop, because the invariant guarantees the front of the array after each pass. Extracting a median from data that may be sorted first invites a strategy question: sorting everything to read the middle costs a full sort, and for the small data in exam problems that is usually the intended path, with the middle index computed as the length divided by two, plus care about what median means when the count is even. Recognizing partial jobs matters because stems phrase them innocently, asking for the kth smallest or the top scores, and the student who sees selection sort's prefix hiding inside the request answers in seconds.

A third variation changes the container mid-question, presenting an algorithm on an ArrayList after teaching it on an array, or the reverse. The traversal skeleton survives; only the access syntax changes, brackets becoming get and set calls, and the length becoming a size call. A fourth variation changes the payload, sorting strings by length rather than alphabetically, or sorting student records by score, which routes comparisons through whatever quantity defines order and tests whether the student can locate the comparison line and re-aim it. Every variation in this family shares one property: the algorithm's movement pattern stays fixed while a single ingredient changes. Students who trace movement patterns absorb variations effortlessly. Students who memorized ingredient lists meet each variation as a brand-new algorithm and run out of memory long before they run out of exam.

Question writers are not being cruel when they bend an algorithm; they are checking whether the student's knowledge is load-bearing. A fact memorized for one configuration collapses under variation, while a mechanism understood from tracing flexes. That is why this guide has spent its pages on frozen states, counts, invariants, and mistakes rather than on polished code recitation. The code is short enough to fit on an index card. The understanding is what fills twenty-one thousand words, and it is the understanding that survives contact with a question nobody has seen before.

## Where These Algorithms Live in Real Programs

It is fair to ask why a course teaches three sorts when production Java offers a built-in sort that beats all of them for general use. The honest answer has two halves. The first half is that the built-in exists and professionals call it, yet professionals who cannot reason about what it costs or why a search needs sorted data make expensive mistakes with it, like sorting a list before every one of a thousand searches or binary searching a list nobody sorted. The second half is that the five procedures in this unit are not really the curriculum. They are the gymnasium. Traversal, invariants, counting, recursion, and boundary discipline are the curriculum, and sorting and searching are simply the most instructive equipment available.

The patterns still surface in recognizable clothing. A teacher's gradebook program keeps a roster sorted by name so a lookup behaves like binary search, and keeps scores in entry order so new results append cheaply, which is insertion thinking without the name. A game leaderboard re-sorts after each round, and because a leaderboard between rounds is nearly sorted already, a real insertion-style pass finishes almost instantly, the adaptivity dividend paid in production. A music application searching a library sorted by artist discards half the catalog with every probe, conceptually if not literally. A contact list on a phone, a parts inventory in a warehouse system, a library catalog: each one makes the same bargain this unit teaches, paying organization costs up front to buy search speed forever.

Scale decides which household names from the unit get invited into real systems. A classroom roster of thirty students would never feel the difference between quadratic and n log n sorting; the quadratic bill is a few hundred comparisons, spent in a blink. A dataset of ten million records turns that same quadratic bill into fifty trillion comparisons, an unusable program, while merge-style sorting handles it routinely and binary search answers lookups in about twenty-four probes. Exam scenario questions scale their stories deliberately, sprinkling phrases like millions of records or thousands of daily lookups to signal which growth family the scenario needs. Students trained to hear those signals as arithmetic, not atmosphere, read the questions the way their writers wrote them.

There is also a defensive reason the unit endures: sorted structure is a contract other code relies on. The moment one part of a program promises that a list is ordered, other parts start assuming it, and a single careless insertion that breaks the order corrupts every binary search downstream, silently. Understanding that contract, when it is established, what maintains it, and what its violation costs, is professional knowledge that no library call can supply. The exam probes the contract from the student side, asking what a search may conclude and what a sort must guarantee. Students who leave the unit thinking in contracts, invariants, and counts have extracted the real content. The sorts were always the vehicle, never the destination.

## Selection Sort Again, With Ties and a Buried Minimum

A second selection run, on less courteous data, exposes behaviors the first run hid. Trace 31, 7, 24, 7, 42, 18, 3, seven values with a duplicated 7 and the minimum buried at the very end. The first pass scans everything, watches the lead change from 31 to 7, holds 7 against 24, holds 7 against the second 7, since a tie never replaces the current champion under a strictly-smaller update rule, holds against 42 and 18, and finally surrenders to 3 at index six. Swapping index six with index zero gives 3, 7, 24, 7, 42, 18, 31. Six comparisons bought that swap, exactly as the count for seven elements predicts on the opening pass.

The second pass scans indices one through six and finds its minimum immediately: the first 7, at index one, is never beaten, because the second 7 merely ties and 18, 24, 31, and 42 all lose. The swap exchanges index one with itself, and the array stands unchanged at 3, 7, 24, 7, 42, 18, 31. Two lessons hide in that stillness. First, the algorithm keeps the earliest copy of a tied minimum, a small mercy that does not rescue its stability in general, since a later swap can still leapfrog copies, as the next passes nearly show. Second, a pass with no visible change is a legitimate trace state, and answer options that always show motion are lying about one pass in most runs.

Pass three scans from index two: 24 leads, the second 7 at index three takes the lead, 42 and 18 fail to beat it, 31 fails, and the swap moves 7 into index two and 24 into index three, producing 3, 7, 7, 24, 42, 18, 31. Pass four scans from index three, finds 18 at index five smaller than 24, and swaps to give 3, 7, 7, 18, 42, 24, 31. Pass five scans from index four, finds 24 at index five, and swaps to give 3, 7, 7, 18, 24, 42, 31. Pass six compares 42 and 31, swaps them, and the run closes at 3, 7, 7, 18, 24, 31, 42. Twenty-one comparisons in total, six plus five plus four plus three plus two plus one, matching the formula for seven elements to the unit. Tracing a run with ties and self-swaps inoculates against the two most common selection misconceptions: that every pass must change the array, and that duplicated minima confuse the hunt. The hunt is never confused. It is a machine for finding the first position of the smallest remaining value, and it finds exactly that, pass after pass, whatever the data does.

## Reading a Trace Backwards

Some of the finest questions in this unit run time in reverse: they display an intermediate state and ask which algorithm, at which step, could have produced it. The two simple sorts make a perfect training pair because their early states overlap just enough to punish shallow pattern matching. Start both algorithms on 29, 10, 14, 37, 13. After selection sort's first pass, the array reads 10, 29, 14, 37, 13, the minimum parked at the front. After insertion sort's first insertion, the array also reads 10, 29, 14, 37, 13, because the second value happened to be the global minimum and slid to the front. Identical states, different machines, and any question stopping there has two defensible answers, which is why well-built questions never stop there.

Ask for the next state and the machines diverge loudly. Selection sort's second pass hunts the minimum of the remainder, finds 13 at the back, and hauls it to index one, producing 10, 13, 14, 37, 29. Insertion sort's second insertion takes 14, the third original value, and tucks it between 10 and 29, producing 10, 14, 29, 37, 13. One state has 13 improbably promoted and 29 exiled to the back; the other keeps every untouched value in its original seat. A student reasoning backwards checks each candidate state against each algorithm's invariant: does the prefix hold the smallest values overall, as selection demands, or merely the earliest values in order, as insertion demands? The state 10, 13, 14, 37, 29 satisfies the first promise and violates the second, because insertion's processed region after two insertions must contain the first three original values, 29, 10, and 14, and the value 13 is not eligible to stand at index one yet.

That eligibility idea generalizes into a fast backwards test. For insertion sort, after k insertions the processed region contains exactly the first k plus one original values, rearranged. For selection sort, after k passes the front region contains exactly the k smallest values of the whole array, wherever they started. For merge sort, states show runs whose lengths are powers of two, with elements drawn from their original neighborhoods. For the searches, backwards questions show low, high, and mid values and ask which target ranges remain possible, and the invariant answers: the target, if present, sits inside the markers, and every probe outside them has been acquitted. Backwards questions feel exotic until the invariant lens is applied, and then they collapse into the same promise-checking exercise as every other question in the unit. That collapse is the deepest available evidence that the invariants, not the code shapes, are the unit's true subject matter.

## The Break-Even Problem: Scan Every Time, or Sort Once?

The unit's most practical question deserves exact numbers. A program holds one hundred unsorted values and must answer searches against them. Strategy one scans sequentially for every query. Strategy two sorts once with a merge sort, then answers every query with binary search. Which strategy wins depends entirely on how many queries arrive, and computing the crossover is a pure application of this unit's counting skills. Start with the scanning bill. A successful sequential search inspects about half the collection on average, call it fifty inspections, and an unsuccessful one inspects all one hundred. A workload of mixed queries therefore bills roughly fifty to one hundred inspections per query, forever, with no upfront cost.

Now the sorting strategy's bill. Merge sort on one hundred values spends on the order of one hundred times seven comparison steps, since one hundred sits between the sixth and seventh powers of two, so budget roughly seven hundred operations once. Binary search on one hundred sorted values needs at most seven probes per query. Five queries under this strategy cost about seven hundred plus thirty-five, roughly seven hundred thirty-five operations, against the scanning strategy's few hundred: scanning wins easily, and sorting for five queries is over-engineering. Two hundred queries reverse the verdict beyond argument. Scanning bills somewhere between ten thousand and twenty thousand inspections, while the sorted strategy bills seven hundred plus fourteen hundred probes, barely two thousand operations in total, an order of magnitude cheaper. The crossover sits near fifteen or twenty queries for this size, and it slides with the data size, arriving earlier as collections grow because scanning's per-query toll grows linearly while the probe toll grows logarithmically.

Three refinements keep the analysis honest. First, if the queries hunt for values that are usually absent, scanning always pays the full one hundred inspections, which drags the crossover toward sorting sooner. Second, if the collection keeps changing, each insertion into a sorted structure costs shifting work, and heavily mutated data can make the sorted strategy bleed its advantage away; stable, read-heavy data is where sorting shines. Third, the sort chosen for the upfront investment matters: paying a quadratic sort's 4,950 comparisons on one hundred values instead of a merge sort's seven hundred pushes the crossover far to the right, punishing small workloads severely. Students who practice break-even arithmetic on round numbers like these find the compressed versions friendly, because the reasoning is identical and only the costumes change.

## Insertion Sort's Worst Case, Counted Exactly

Because insertion sort's bill floats with the data, its extremes deserve exact arithmetic rather than gestures. The worst case arrives when the data stands in perfect reverse order, because every new value must travel the entire width of the sorted prefix before stopping at the front edge. On ten reversed values, the insertions demand one, two, three, and so on up to nine comparisons, summing to forty-five, and the shifts match the comparisons one for one, another forty-five. The comparison total equals selection sort's immutable total for the same size, n times n minus one over two, with a mountain of shifts stacked on top. Reverse order is the cruelest gift data can give this algorithm, and exam writers hand it over constantly.

The average case falls between the extremes in an instructive place. On randomly ordered data, a new value travels about halfway into the prefix on average, so comparisons and shifts each total roughly a quarter of n squared, half the worst-case bill. Ten random values therefore cost around twenty-two comparisons rather than forty-five or nine. That middle figure explains why insertion sort enjoys a respectable practical reputation on small, casually ordered datasets despite sharing a growth family with its worst case: constants and averages govern lived experience at small scales, even while growth families govern destiny at large ones. The exam tests both lenses, asking for exact counts on given data, where tracing rules, and for family-level predictions on growing data, where the doubling behavior rules.

Selection sort deserves one final counting observation to complete the symmetry. Its comparison total is not merely fixed; it is identical to insertion sort's worst-case total, a coincidence of sums, since both equal the sum of the integers from one to n minus one. A counting question that reports forty-five comparisons on ten elements has therefore not identified its algorithm yet: the number fits selection sort on any data and insertion sort on reversed data. The follow-up evidence must come from swaps and shifts, or from the arrangement of the data given in the stem. Students who notice that ambiguity in practice questions stop treating raw comparison totals as fingerprints and start treating them as one clue among several, which is precisely the sophistication the unit's hardest questions are built to measure.

## Sorting Strings: The Alphabet's Fine Print

String comparisons carry fine print that numeric comparisons never warned anyone about, and compareTo questions mine that fine print happily. Comparison proceeds character by character from the left, and the first position where two strings differ decides their order, with the decision made by the characters' underlying numeric codes rather than by any human notion of the alphabet. Those codes produce two famous surprises. Every uppercase letter carries a smaller code than every lowercase letter, so a capital Z sorts before a lowercase a, and a roster sorted naively from mixed-case input groups all the capitalized names before all the lowercase ones. Digits behave as characters too, so the string 10 sorts before the string 9, because the opening characters 1 and 9 compare first and 1 wins, a result that baffles anyone expecting numeric order from text.

Length enters only after a shared prefix is exhausted. A shorter string that matches the beginning of a longer one sorts first: Ann before Anna, art before article. When strings differ early, length never gets a vote. The exam exploits these rules through ordering questions that hand students a fistful of strings and ask for sorted order or for the sign of a particular compareTo call. The reliable method mirrors everything else in this unit: write the strings in a column, scan for the first differing position in each pair, and let that single character decide, refusing to let word meanings or numeric intuitions vote. Students who try to sort strings the way a dictionary feels, rather than the way the codes dictate, donate points to precisely the traps the writers set.

These details loop back to the algorithms unchanged, which is the consoling part. Selection sort does not care whether its comparisons examine integers, names, or names with capital-letter traps; the hunt, the swap, and the invariant survive translation perfectly. Insertion sort slides strings with compareTo playing the operator's role, still stopping at equals, still stable. Binary search on a string collection demands the collection be sorted by the same comparison the search uses, and a collection sorted case-insensitively by a human but searched case-sensitively by code is a contract violation waiting to return negative one for names that are plainly present. The algorithms are comparison-agnostic; the comparisons themselves are where string data hides its teeth.

## A Ladder of Sizes: Feeling the Growth Families

Growth families stop being abstractions when they are climbed rung by rung. Stand at ten elements first. Selection sort spends forty-five comparisons, insertion sort spends somewhere between nine and forty-five, merge sort spends a few dozen operations, sequential search averages about five inspections, and binary search needs at most four probes. At this altitude every algorithm feels instant and interchangeable, which is why toy examples alone cannot teach the unit: the differences that matter have not switched on yet.

Climb to one hundred elements and the families begin separating. Quadratic comparison counts reach 4,950 for selection sort and for insertion sort's worst case. Merge sort spends roughly six hundred sixty comparison steps. Sequential search averages fifty inspections per successful hunt. Binary search needs at most seven probes. Nothing here is slow in human terms, yet the ratios have already declared themselves: the quadratic bill is about seven times the merge bill, and the probe count has barely noticed the tenfold growth in data. Climb to one thousand and the separation turns dramatic. Quadratic counts approach half a million. Merge sort spends roughly ten thousand steps. Sequential search averages five hundred inspections. Binary search needs at most ten probes.

The top rung, one million elements, is where the families stop being comparable at all. A quadratic sort owes on the order of five hundred billion comparisons, a workload measured in hours or worse, while merge sort owes on the order of twenty million steps, finished in moments, and binary search answers any single question in at most twenty probes. Sequential search averages half a million inspections per hunt, tolerable once and ruinous across millions of hunts. Memorizing this ladder is unnecessary; understanding why each rung's numbers follow from each algorithm's mechanism is the entire game. Halving processes add steps in single digits per tenfold growth. Scanning processes multiply by ten. Whole-collection rescans multiply by a hundred. A student who can regenerate the ladder from mechanisms owns the efficiency third of this unit outright, and scenario questions reduce to matching a story's scale against a ladder the student can rebuild at will.

## Checksums: Verifying a Trace Before Trusting It

A finished trace should never be trusted on vibes, because the unit supplies mechanical checks that catch most errors in seconds. The strongest is the permutation check: sorting rearranges values, so the multiset of values after any pass must equal the multiset before it. A trace step that loses a value or duplicates one has committed the classic swap error, and counting how many times each distinct value appears, before and after, exposes the crime immediately. Searching changes no values at all, so any search trace whose array differs between probes is wrong by construction, no further inspection needed.

Count checks form the second layer. A completed selection run on n elements must show exactly n minus one passes and n times n minus one over two comparisons; a trace reporting anything else contains a bookkeeping error somewhere. A binary search on n elements can never legitimately exceed the number of halvings that reduces n to one, plus one final probe, so a trace wandering past that budget has failed to shrink its interval correctly somewhere. A merge run's levels must equal the number of times the size can be halved down to single elements, rounded up, and each level must place every element exactly once. Running these arithmetic checksums takes moments and converts the sick feeling of uncertainty into a list of verified or flagged steps, each flagged step a precise address for repair. Professional programmers call this habit sanity checking, and it scales from five-element exam traces to production systems without changing its character at all.

Two qualitative checks complete the kit. A sorting trace must end in genuinely sorted order, verified by a single left-to-right scan of the final state confirming that no adjacent pair stands inverted; a surprising number of wrong traces end one swap away from order and confess it under that scan. A search trace must end in a defensible verdict: either the returned index actually holds the target when checked against the original data, or the markers have genuinely crossed with every region outside them provably examined and acquitted. Checking the verdict against the original data, rather than against the traced data, catches the quiet catastrophe of a trace that corrupted its own array early and then reasoned flawlessly about the corruption.

## A Study Plan That Builds the Tracing Habit

Preparation for this unit should look like the unit itself: structured, repetitive in the right places, and always verified. Begin with blank-paper reproductions. Write each algorithm's code from understanding rather than memory, then immediately test the written code by tracing it on a small array with a personality: some duplicates, a value that belongs at the very front, a value already in place. Code that survives hostile little arrays earns trust. Code that fails gets repaired on the spot, and the repair teaches more than the original writing did. Rotating through the five procedures this way, a few arrays each, builds the code fluency free-response questions demand.

Layer counting practice on top of the tracing practice. For every traced run, tally comparisons and moves in the margin, then compare the tallies against the predictions from the reference table: selection sort's fixed total, insertion sort's floating total, merge sort's level-by-level total, the searches and their probe counts. Prediction followed by verification is the engine of the whole method. When a tally disagrees with a prediction, the disagreement is a gift; it marks the exact step where understanding thins, and re-tracing that single run usually thickens it. Timed drills come last, and they should mix algorithms randomly, because the exam never announces which procedure a stem is secretly about. ## Frequently Asked Questions

### Q: What sorting algorithms are on AP Computer Science A?

The AP Computer Science A exam covers three sorting algorithms by name: selection sort, insertion sort, and merge sort. Selection sort repeatedly finds the smallest unsorted value and swaps it into place. Insertion sort builds a sorted prefix by sliding each new value into position among those already placed. Merge sort divides the data in half, sorts each half recursively, and merges the sorted halves. Students are expected to trace all three on paper, compare their efficiency, and write code for the two simpler sorts, while merge sort questions emphasize tracing, recursion structure, and cost reasoning rather than full implementation from memory. Other sorts that students may have heard of, such as bubble sort or quicksort, are not part of the required curriculum, although a question could present unfamiliar pseudocode and ask for a trace, since tracing skill transfers. Knowing which three algorithms carry the course's weight helps students allocate study time: deep fluency in selection and insertion, strong conceptual command of merge sort, and the comparison and counting vocabulary that ties all three together on efficiency questions in both multiple-choice and free-response sections.

### Q: How does selection sort work on AP Computer Science A?

Selection sort divides the data into a sorted prefix and an unsorted remainder, then grows the prefix one pass at a time. Each pass scans the entire remainder, remembers the index of the smallest value found, and swaps that value into the first position of the remainder. After the first pass, the smallest value in the whole collection sits at index zero and never moves again. After the second pass, the two smallest values occupy the first two positions in order, and so on. A run on n elements needs n minus one passes, because the final remaining value is automatically the largest and already in place. The scan compares every pair it crosses, so the comparison total is fixed at n times n minus one over two regardless of how the data starts, while swaps stay below one per pass. On the array 29, 10, 14, 37, 13, the passes park 10, then 13, then leave 14 where it stands, then swap 29 ahead of 37, finishing in four passes. The algorithm's invariant, that the prefix always holds the smallest values in final order, is what trace questions test.

### Q: How does insertion sort work on AP Computer Science A?

Insertion sort builds a sorted prefix from the values it has already seen, the way a card player organizes a hand one card at a time. It lifts the next unprocessed value into a variable, then walks leftward through the prefix, shifting every larger value one position to the right, and stops when it finds a value that is smaller than or equal to the lifted value, or when it reaches the front of the array. The lifted value drops into the vacated slot, and the prefix has grown by one, still in order. Unlike selection sort, the prefix does not hold the smallest values overall and its positions are not final, because a later small value can insert itself near the front and push residents rightward. On 29, 10, 14, 37, 13, the value 10 shifts 29 rightward and takes the front, 14 slips between 10 and 29, 37 stays where it sits, and 13 shifts three larger values before settling at index one. Because each insertion can stop early, the algorithm runs quickly on nearly sorted data and slows to a quadratic worst case on reversed data.

### Q: How does merge sort work on AP Computer Science A?

Merge sort sorts by dividing and merging rather than by hunting or inserting. It splits the data into two halves, sorts each half by applying the same splitting process recursively, and stops splitting when it reaches pieces of a single element, which are sorted by definition. Then it merges neighboring pieces: two pointers walk the fronts of two sorted runs, repeatedly copying the smaller front value into the output, and when one run empties, the remainder of the other run copies across without further comparisons. Small ordered runs double in size at each level until one run covers everything. On 8, 5, 9, 1, 7, 3, the left half becomes 5, 8, 9, the right half becomes 1, 3, 7, and the final merge weaves them into 1, 3, 5, 7, 8, 9. Each level of merging touches every element once, and the number of levels grows logarithmically, so total work grows as n log n. The trade-offs are extra memory for the merge output and no speedup on data that arrives already sorted, since the splitting and merging effort never diminishes.

### Q: How does binary search work on AP Computer Science A?

Binary search locates a target in sorted data by repeatedly halving the interval where the target could hide. Two markers, low and high, start at the first and last indices. The algorithm probes the midpoint of the interval, computed with integer division. If the midpoint value equals the target, the search returns that index. If the target is larger, every position at or below the midpoint is eliminated and low moves one past the midpoint. If the target is smaller, high moves one below the midpoint. The loop continues while low stays less than or equal to high, and if the markers cross without a match, the method returns negative one to report absence. On the array 3, 8, 12, 19, 25, 31, 42, 56, 67, 80, searching for 42 probes index four and finds 25, then index seven and finds 56, then index five and finds 31, then index six and finds 42, finishing in four probes. Because each probe halves the surviving interval, a thousand sorted values need at most ten probes, and doubling the data adds exactly one probe to the worst case.

### Q: How does sequential search work on AP Computer Science A?

Sequential search, also called linear search, inspects values one at a time starting from index zero and stops at the first match. The standard implementation loops an index across the whole structure, compares the value at that index against the target, and returns the index immediately when a comparison succeeds. If the loop finishes without a match, the method returns negative one, the conventional signal that the target is absent. That is the entire mechanism, and its simplicity is the point: the algorithm asks nothing of the data, which may be unsorted, partly sorted, or freshly shuffled. On 29, 10, 14, 37, 13, finding 13 costs five comparisons because the target sits last, finding 29 costs one, and hunting the absent value 20 costs five before the negative one verdict. Averaged across successful searches, about half the collection gets examined, so the expected work grows linearly with size. The exam uses sequential search as the baseline every other method is compared against, and as the correct choice when data is unsorted, when a search happens only once, or when the collection changes too often to maintain in sorted order.

### Q: How do you trace a sorting algorithm on AP Computer Science A?

Tracing a sorting algorithm means simulating it on paper with enough bookkeeping that no step depends on memory or intuition. Draw the array as boxes with indices labeled, and keep a running table of the variables: the outer index, the inner index, and whichever extra variable the algorithm carries, such as the position of the current minimum or the value being inserted. Work pass by pass, updating the array only at the moments the algorithm itself moves values, and write the new state after each pass rather than erasing the old one, since questions often ask about intermediate states. Verify each pass against the algorithm's invariant before moving on: a selection pass must end with the next smallest value parked at the boundary, and an insertion must end with the prefix holding the processed values in order. When a candidate answer state appears in a multiple-choice list, test it against the invariant first, because distractors usually violate an invariant in a specific way, such as showing insertion sort's prefix containing a value it has not processed yet. Finish by checking that the final state is a permutation of the original data and fully sorted.

### Q: What is the difference between binary and sequential search on AP Computer Science A?

The two searches differ in precondition, behavior, and cost, and exam questions test all three differences at once. Sequential search makes no demands: it starts at index zero, examines values in order, and works on any data whatsoever, sorted or not. Binary search absolutely requires sorted data, because its decision to discard half the interval after each probe is only valid when order guarantees that the discarded half cannot contain the target. Behavior differs just as sharply. A sequential scan touches values one by one and never skips any, while binary search leaps to midpoints and never examines most values at all. Cost follows from behavior: sequential search examines about half the collection on an average successful hunt and all of it on a miss, growing linearly, while binary search needs at most about log base two of the size in probes, so a million sorted values surrender to roughly twenty probes instead of an average of half a million inspections. Both return an index on success and negative one on failure. Choosing between them means asking whether the data is sorted, how large it is, and whether sorting it once will be repaid across enough searches.

### Q: How do you choose between sorting algorithms on AP Computer Science A?

Choosing a sorting algorithm on the exam means matching the algorithm's profile to the properties the question gives the data. Selection sort spends the same fixed number of comparisons on every input and performs very few swaps, so it suits scenarios where moving data is expensive, comparisons are cheap, or a question asks for the front portion sorted, since a few passes park the smallest values at the front. Insertion sort adapts to the input: it flies through nearly sorted data with about one comparison per element, handles small collections gracefully, and accepts values one at a time, but collapses to a quadratic worst case on reversed data. Merge sort guarantees n log n work on every input and stays stable, at the price of extra memory for merging and no benefit when data arrives sorted. Size is the loudest signal in most scenarios: small data makes every algorithm acceptable, while large data eliminates the quadratic pair. A need for stability points toward merge or insertion, and a memory constraint points toward the in-place pair. Read the stem for its gifts and its constraints, then name the algorithm whose strengths answer them.

### Q: How is algorithm efficiency tested on AP Computer Science A?

Efficiency on this exam is tested informally, through counting and comparison rather than through formal proofs or notation drills. Multiple-choice questions ask how many comparisons, swaps, iterations, or probes a described run performs, which reduces to loop arithmetic and careful tracing: multiplying an outer loop's count by an inner loop's count, adjusting for bounds that shrink each pass, and summing the arithmetic sequence when a count decreases steadily. Other questions describe two algorithms or two input sizes and ask which run costs more, or what happens to the workload when the data doubles, which tests the growth families: linear work doubles, quadratic work roughly quadruples, n log n work slightly more than doubles, and logarithmic work grows by a single step. Free-response parts occasionally reward a reasonably efficient approach, but the heavy efficiency traffic is multiple-choice counting. Students prepare by tallying comparisons and moves during every practice trace and by checking totals against known formulas, such as selection sort's fixed n times n minus one over two comparisons. Nothing is measured in seconds, because operation counts live entirely inside the printed code and data, making them perfectly standardized for an exam.

### Q: How do you implement selection sort in code on AP Computer Science A?

The standard implementation nests two loops around a single swap. The outer loop runs an index i from zero to one less than the second-to-last position, marking the sorted boundary. Before the inner loop starts, a variable minIndex is set to i, recording where the smallest value seen so far in this pass lives. The inner loop walks a second index j from i plus one to the end of the array, and whenever the value at j is smaller than the value at minIndex, minIndex updates to j. Carrying the index rather than the value is essential, because the pass ends with a swap that needs both positions. After the inner loop, a temporary variable swaps the values at i and minIndex, parking the pass's minimum at the boundary. Two details decide correctness under grading: the swap must sit outside and after the inner loop, not inside it, and the inner loop must start at i plus one, never at zero, so finished prefix positions are never disturbed. Written this way, the method sorts any int array in place, and the same shape works for ArrayLists with get and set replacing bracket access.

### Q: How does merge sort use recursion on AP Computer Science A?

Merge sort is the course's flagship recursive algorithm, structured as a base case and two smaller calls wrapped around a merge. The base case is a segment of length one or zero, which is already sorted and returns untouched. The recursive case computes the midpoint of the current segment, calls the sorting method on the left half, calls it on the right half, and then merges the two now-sorted halves into order. Each call therefore spawns two child calls, forming a tree whose depth is the number of times the data can be halved, and the merging work happens as calls return, flowing from the leaves back up to the root. A call sorting six elements calls down to singles, merges pairs into ordered runs of two, merges those into runs of three on each side, and merges the sides one final time. Exam questions about this structure ask students to identify the base case, count levels or calls, predict intermediate run contents, and reason about what happens if the base case is removed, which is an infinite recursion ending in a stack overflow. The recursion supplies the dividing; the merge supplies the sorting; neither half works alone.

### Q: Which array operations support sorting on AP Computer Science A?

Every sort in the unit is assembled from a small kit of array operations, and fluency with the kit predicts fluency with the algorithms. Indexed access reads the value at a position, the raw material of every comparison. Indexed assignment writes a value into a position, overwriting the previous occupant, and it is the primitive beneath swaps and shifts. A swap is three assignments coordinated through a temporary variable: copy one value aside, overwrite its slot, then write the parked value into the other slot. A shift is an assignment that copies a value into a neighboring slot, used in runs by insertion sort, always proceeding from the end nearest the gap so values are not overwritten before being copied. Length access bounds every loop, with the last valid index always one less than the length. Traversal patterns tie the kit together: full forward walks for scanning, shrinking walks for selection passes, backward walks for insertion shifting, and midpoint jumps for binary search. On ArrayLists the same kit appears with method syntax, get for access, set for assignment, size for the bound, and add with an index performing an automatic shift of the tail.

### Q: How do you trace the steps of binary search on AP Computer Science A?

Tracing binary search means tracking three variables in a small table, one row per probe: low, high, and the midpoint computed from them. Start with low at the first index and high at the last index, then for each row compute mid as the sum of low and high cut in half with integer division, and compare the target against the value stored at mid. A larger target moves low to mid plus one; a smaller target moves high to mid minus one; an equal value ends the trace with mid as the answer. The trace of a miss ends when low passes high, proving the interval empty. On 3, 8, 12, 19, 25, 31, 42, 56, 67, 80 with target 30, the rows read: markers zero and nine probe 25, so low rises to five; markers five and nine probe 56, so high falls to six; markers five and six probe 31, so high falls to four; the markers have crossed and the search returns negative one. Writing one row per probe matters because exam distractors are built from skipped rows and stale markers, and a complete table makes both errors visible at a glance.

### Q: What sorting and searching mistakes are common on AP Computer Science A?

The recurring mistakes form a short rogues' gallery, and every member is a boundary or bookkeeping slip rather than a deep misunderstanding. Off-by-one errors lead the list: loops running to the length instead of stopping one short, a high marker initialized to the length rather than the last index, and pass counts of n instead of n minus one. Swap errors follow: omitting the temporary variable so one value overwrites the other, or placing the swap inside selection sort's inner loop so swaps fire constantly instead of once per pass. Binary search contributes marker errors, updating low or high to the midpoint itself instead of one position past it, which can strand the loop probing the same element forever, and the conceptual error of running binary search on unsorted data and trusting whatever it returns. Insertion sort contributes direction errors, shifting values in the wrong order so one value smears across the prefix, and dropping the guard that stops the walking index below zero. Merge sort contributes the forgotten leftover, where the tail of the longer run never copies into the result. Each error survives memorized code and dies under careful tracing.

### Q: How do the runtimes of the AP Computer Science A sorts compare?

The three sorts separate into two growth families, and one member straddles them depending on the data. Selection sort always performs n times n minus one over two comparisons, a quadratic count that never varies with the input's arrangement, while keeping swaps under n. Insertion sort matches that quadratic total in its worst case, reversed data, but falls to about n comparisons on sorted data and averages roughly a quarter of n squared on random data, with shifts tracking the comparisons closely. Merge sort spends n log n work in every case, best, worst, and average alike, trading extra memory for that consistency. Concretely: on one hundred elements, selection sort spends 4,950 comparisons, insertion sort spends between one hundred and 4,950, and merge sort spends roughly six hundred sixty steps. On one million elements the quadratic pair owes on the order of five hundred billion comparisons while merge sort owes on the order of twenty million. Doubling the data roughly quadruples either quadratic bill, slightly more than doubles the merge bill, and leaves the ranking untouched. The exam tests these comparisons as counts on traced runs and as doubling predictions on growing inputs.

### Q: Why does binary search require a sorted array on AP Computer Science A?

Binary search's every decision rests on a promise that only sorted data can keep. When the algorithm probes the midpoint and finds a value smaller than the target, it discards the entire left half of the interval, including the midpoint, in a single step. That discard is safe only because sorted order guarantees that everything left of the midpoint is smaller than or equal to the midpoint value, and therefore smaller than the target as well. Remove the ordering and the guarantee evaporates: a value larger than the midpoint can sit anywhere to its left, so the discarded half might contain the target, and the algorithm can march confidently away from the answer. The code still compiles and runs on unsorted data, returning indices and negative ones with total confidence, which is what makes the trap dangerous rather than merely broken. A search might even succeed by luck, reinforcing false trust. Exam questions exploit this by pairing binary search code with unsorted data and asking for the returned value, which can only be found by tracing the code mechanically. Sorting is not a preference for binary search; it is the premise the whole proof stands on.

### Q: How does insertion sort differ from selection sort on AP Computer Science A?

Both algorithms grow a sorted prefix at the front of the array, and nearly everything else about them differs. Selection sort fills its prefix with the smallest values of the entire collection, found by scanning the whole unsorted remainder on every pass, and each prefix position is final the moment it is filled. Insertion sort fills its prefix with the first values it encountered, arranged in order among themselves, and those positions stay provisional because a later value can insert itself anywhere in the prefix and shift residents rightward. Their work profiles diverge in consequence. Selection sort performs the same number of comparisons on every input of a given size and swaps at most once per pass. Insertion sort lets both comparisons and shifts float with the data, performing a single comparison per element on sorted input and a quadratic flood of both on reversed input, and it moves data by shifting rather than swapping. A frozen mid-run state exposes the difference instantly: selection's prefix holds global smallest values with an untouched remainder behind it, while insertion's prefix holds early original values, fully ordered, above the same untouched remainder. Questions built on that contrast reliably separate memorizers from tracers.

### Q: How do you search an ArrayList on AP Computer Science A?

Searching an ArrayList uses the same algorithms as searching an array, with method calls standing in for bracket notation. A sequential search loops an index from zero up to one less than the size, comparing the target against the element returned by get at each index, and returns the index of the first match or negative one after the loop. The size method replaces the length field everywhere it appears, and the last valid index remains the size minus one. When the list holds objects, comparisons route through equals rather than the equality operator, because the goal is an element with matching content, not the identical object in memory. The built-in indexOf method performs exactly this sequential scan and returns the first matching index, relying on the element class's equals method to define a match, and lastIndexOf performs the same scan from the end. Binary search applies to a list only when its elements stand in sorted order, and the marker arithmetic transfers unchanged, with get supplying each probed value. Exam questions move freely between arrays and ArrayLists while keeping the algorithm fixed, because traversal, comparison, and boundary logic survive the container swap intact.

### Q: What happens when binary search misses its target on AP Computer Science A?

A miss unfolds as an orderly narrowing that ends with the markers crossing. Each probe compares the midpoint value against the target and eliminates half the interval, so the surviving interval shrinks toward the exact spot where the target would belong if it existed. Eventually a probe examines the last candidate position, finds a near neighbor instead of the target, and the update moves low one past high or high one below low. At that moment the interval is empty, which constitutes a proof of absence: every position has either been probed directly or eliminated by a comparison whose verdict sorted logic guarantees. The loop condition, low less than or equal to high, fails, the loop exits without executing a return, and control reaches the return statement after the loop, which yields negative one. That negative one is not an error state; it is the designed answer meaning the target occurs nowhere in the data. The probes consumed by a miss are the maximum the search ever spends, about log base two of the size rounded up, since success can exit early on a lucky probe while a miss must squeeze the interval completely dry.
