Most of AP Computer Science Principles asks students to reason about programs that other people wrote. The Create Task reverses the direction. Inside a set window of class time, each student designs and builds a program of their own, records a short video of that program running, and writes responses that explain the thinking embedded in the code. The subject of the program is the student's choice, the language is the student's choice, and the design decisions are the student's responsibility from the first sketch to the final check. That freedom is the point of the task, and it is also where the difficulty lives, because nobody hands the student a prompt narrow enough to hide inside.

The three pieces of the submission work as one argument presented in three forms. A working program embodies a set of decisions about data, structure, and behavior. A video demonstrates that the program genuinely runs and responds to input the way its author claims. Written responses then explain why the code is organized as it is, where its important ideas live, and how its central algorithm behaves. Readers score the submission by looking for evidence across all three pieces, so a strength in one place cannot fully rescue a silence in another. Students who grasp that unity early tend to find the whole task calmer, because every hour of coding doubles as preparation for the writing.

Planning is the skill that separates comfortable finishes from frantic ones. The window for the work is fixed, the requirements are published in advance, and the difference between a strong submission and a thin one is rarely raw coding talent. Strong submissions come from students who chose an idea sized to the window, designed their list and their main procedure before the code grew tangled, and treated the written responses as a parallel product rather than a chore appended at the end. This guide follows that arc in order: the shape of the task, the choice of an idea, the program requirement, the list, the procedure, the algorithm, the video, the responses, and a checklist that carries a project from first sketch to submission. For the course as a whole, the companion [guide to AP Computer Science Principles](/2008/06/26/ap-computer-science-principles-guide/) covers the concepts and the end-of-course exam that surround this task.

## One Task, Three Artifacts

The program comes first in every sense. It must run, it must accept input, and it must produce output, and it must do something its author can describe as a purpose. A program for the Create Task is not a loose collection of practice exercises stitched together; it is a single coherent piece of software built to accomplish a goal the student can state in a sentence or two. Games, simulations, quizzes, planners, data explorers, creative generators, and study tools all qualify when they are built with genuine structure. What matters is not the genre but the presence of real decisions inside the code, because those decisions are what the rest of the submission exists to explain.

A video accompanies the code and shows the program in action. Its job is proof of life: the viewer watches input enter the program and output come back, following the main path the author designed. A reader who cannot run the code personally still needs confidence that the program behaves as described, and the recording supplies that confidence in the author's own demonstration. Students sometimes treat the video as an afterthought squeezed into the final session, which is a mistake the planning section of this guide works to prevent. The demonstration deserves rehearsal, because a fumbled recording of a good program reads as uncertainty about the program itself.

Written responses complete the trio, and they carry far more weight than their modest length suggests. In the responses, the student describes the program's purpose and function, explains the data abstraction captured in a list, explains the procedural abstraction captured in a procedure the student wrote, and walks through an algorithm that combines sequencing, selection, and iteration. Every claim in those responses points back at specific code, so the writing is really a guided tour of the submission's best ideas. A student whose code contains a thoughtful list, a clean procedure, and a genuine algorithm will find the responses almost write themselves, while a student whose code lacks those features has nothing solid to point at.

Originality is a hard boundary around all three artifacts. The program and the responses must be the student's own work, produced for this task, in the student's own words and code. Borrowed material has a legitimate place in programming, and a later section of this guide explains how to credit code that was adapted from elsewhere, but the core of the submission, the parts the responses describe and claim, has to originate with the student. Teachers can support the process in defined ways, and classmates can discuss ideas in general terms, yet the artifact that goes out under a student's name must represent that student's decisions.

One further fact shapes how a student should use any guide, including this one. The College Board publishes the requirements and scoring guidelines for the Create Task, and those documents can change from year to year as the course evolves. Requirements described here reflect the enduring structure of the task: a program, a video, and written responses built around a list, a procedure, and an algorithm. Before beginning, a student should read the guidelines in force for their own year and let those documents settle any detail where a summary and the source might differ. Habits of verification matter in computer science generally, and this task quietly rewards them.

### What should a student settle before writing the first line of code?

Settle the program's purpose, its input, and its output, in plain sentences a classmate could repeat. Decide which collection the program will store in a list, which repeated job deserves its own procedure, and which branching stretch of code will serve as the featured algorithm. Everything afterward refines those early choices.

## Choosing an Idea That Fits the Window

Every Create Task begins as an idea, and the idea quietly determines almost everything that follows. A well chosen project makes the list obvious, the procedure natural, and the algorithm easy to exhibit. A poorly chosen one forces the student to bolt those features onto a program that never wanted them, and readers can feel the strain in the written responses. Choosing well is therefore not a preliminary nicety. It is the first scored decision of the task, made before a single line of code exists, and it deserves the same care as any debugging session later on.

Interest is the first filter, and it is more practical than sentimental. The student will live inside this program across many class sessions: designing it, building it, breaking it, fixing it, filming it, and writing about it. A topic the student genuinely cares about sustains attention through the tedious middle sessions when the code is half built and nothing quite works. A topic chosen to impress, borrowed from a friend's enthusiasm or a teacher's example, tends to go stale at exactly the wrong moment. Personal knowledge helps as well, because a student who understands the domain, whether that domain is basketball statistics, houseplant care, or a family recipe collection, spots nonsense in the program's behavior that a stranger would miss.

Scope is the second filter, and the harder one to judge. Ambition feels virtuous at the start of the window and expensive near its end. The useful test is whether the student can describe the finished program's core behavior in a short paragraph and can name the features that would be cut first if time ran short. A project with a clear core and optional decorations survives trouble; a project whose every feature is load bearing collapses when one piece resists. Experienced builders describe this as finding the smallest version that still fulfills the purpose, then treating everything else as an upgrade to add only when the core runs cleanly.

Input and output deserve thought at the idea stage, because the task requires both and the video must show both. Some ideas produce input naturally: a quiz takes answers, a planner takes dates and tasks, a simulation takes starting conditions, a game takes moves. Other ideas sound appealing but leave the student hunting for something the user can supply and something the program can return. A drawing toy with no decisions, a slideshow with no choices, or a page of static facts may be pleasant software and still make a weak Create Task, because the required structures have nowhere to live. Asking, at the idea stage, what the user gives and what the user gets back eliminates a whole family of later regrets.

Certain families of projects recur in classrooms because they fit the requirements gracefully. A quiz or trivia program stores its questions and answers in a list, uses a procedure to run a round, and lets an algorithm score responses with branching and repetition. A personal organizer stores entries in a list, uses a procedure to add or search entries, and filters or sorts them through an algorithm the student can narrate. A simulation stores agents, particles, or grid cells in a list and advances them under rules that mix decisions with loops. A creative generator stores words, colors, patterns, or sounds in lists and assembles them under constraints. None of these families is required, and originality within any of them is welcome, but each one demonstrates that the requirements are not obstacles. They are descriptions of how real programs are already built.

Ideas fail in predictable ways, and naming the failures early is cheap insurance. The most common failure is scale: a role playing game with a world map, an inventory system, combat, dialogue, and saved games is five projects wearing one coat. Another failure is dependence on machinery the student does not control, such as a live data feed, an unfamiliar library, or a collaborator's unfinished component. A third failure is thinness dressed as simplicity, a program so small that its list holds three items the code never processes and its algorithm is a single comparison. Readers respond to substance, and substance requires a program that actually does something with its data.

A practical way to test an idea is to sketch the program's life on paper before coding. Write the purpose in one sentence. List the inputs with their sources, then the outputs with their destinations. Name the collection that will live in a list and describe what the program does with that collection. Point at the job that repeats often enough to deserve a procedure. Describe, in ordinary words, the sequence of steps with its decisions and its loop. If the sketch fills a page comfortably and every requirement has a home, the idea is probably sound. If the sketch stalls on any element, the stall is information, and it arrives while changing direction is still free.

Students sometimes worry that a modest idea signals modest ability. The opposite is closer to the truth. Readers score evidence of specific skills, and a compact program can display every one of them with unusual clarity, because nothing hides. A sprawling program with half finished systems displays mainly sprawl. Choosing an idea that fits the window, the student's knowledge, and the requirements is itself a demonstration of the judgment the course tries to teach, and it sets up every section that follows in this guide.

## Three Genres in Depth

Genres organize expectations, and examining three reliable families in detail shows how the requirements take different shapes while remaining the same requirements. Begin with the quiz and game family, the classroom's most familiar inhabitant. The list holds the game's content: questions with their answers, cards with their values, words with their definitions, levels with their configurations. The central procedure runs a round: presenting an item, accepting a response, judging it, updating the score. The featured algorithm usually governs progression and judgment together, deciding from the pattern of answers whether to advance, repeat, raise the difficulty, or end the game, with a loop carrying the round structure and branches handling correctness, streaks, and boundaries.

Games fail in a characteristic way worth warning against: the content list gets built and displayed while the game's logic stays trivial, so the program is a slideshow with a score variable. The remedy is to design the judgment first. What makes an answer partially right, what ends a round early, what pattern of success changes the next item's difficulty? Questions like those give the algorithm decisions worth explaining. A quiz whose difficulty adapts, whose questions are drawn without repetition from the list, and whose final report names the categories where the player struggled is the same genre at full strength, and the distance between the two versions is entirely design attention.

The data tool family covers planners, trackers, logs, and collection managers, programs whose purpose is to keep records and answer questions about them. The list is the record collection itself, and entries arrive through the entry pattern with validation. Procedures add, edit, search, and summarize. The featured algorithm usually produces the tool's signature answer: the recommendation, the filtered view, the summary with its totals and extremes. This family's great virtue is honest work for every structure, since a tool that never computes over its records is a notebook, and its great risk is the opposite excess, a feature list borrowed from commercial software that the window cannot hold.

Data tools reward a particular design conversation about the questions the records should answer. A reading log that can report the reader's pace per genre invites different storage choices than one that merely lists titles. Deciding the signature questions early tells the student which fields each record needs, which is far cheaper than discovering a missing field after fifty entries exist in the wrong shape. The response about the list practically drafts itself from that conversation, because the student can explain not just what the collection holds but why each element carries the fields it does.

The simulation and generator family trades records for behavior. The list holds the world's inhabitants or materials: agents with positions and states, cells in a grid, particles, or the word banks and pattern pieces a generator assembles. A step procedure advances the world by one tick, applying the rules to every element. The featured algorithm is usually the rule engine itself, the loop that visits each inhabitant and applies branches based on neighbors, resources, or chance constrained by the user's settings. This family produces the most watchable videos, because the world visibly evolves, and it demands the most testing discipline, since emergent behavior can surprise even its author.

Generators add a twist: their output is an artifact, a story, a workout, a melody sketch, a study set, assembled from the lists under constraints the user sets. The algorithm's branches enforce the constraints, its loops assemble the pieces, and its quality is judged by whether the artifacts feel varied without feeling random in the wrong places. A generator whose constraints are genuine, no repeated element, difficulty rising across the artifact, categories balanced, gives the student an algorithm with real decisions to narrate. Simulations and generators both punish vagueness about stopping conditions, so the design sketch for this family should always answer one question explicitly: what makes a run end?

Across all three families, the pattern from the series thesis holds without exception. The projects that finish strong are the ones where the list, the procedure, and the algorithm were designed as the program's skeleton rather than discovered in its remains. Genre knowledge helps a student borrow a skeleton with confidence, and the borrowing that matters here is of shapes, not of code: shapes are the common inheritance of programmers, while the code that fills them must be the student's own.

## The Program Requirement in Depth

Strip away the surrounding artifacts and the program requirement sounds simple: build a working program, in a language of the student's choosing, that takes input and produces output in service of a purpose. Each clause of that sentence carries weight. Working means the program runs without crashing on the paths the student demonstrates and describes. The language choice is genuinely open, since classrooms build in block based environments, in Python, in JavaScript, and in other languages besides, and the scoring guidelines care about the ideas in the code rather than the dialect expressing them. Input and output mean the program responds to the world outside itself rather than merely unfolding a fixed script.

Purpose is the clause students most often undervalue. A purpose is not a topic. "My program is about music" names a topic, while "my program helps a practice session by generating chord progressions at a chosen difficulty and quizzing the player on them" names a purpose with a user, an action, and a benefit. The written responses will ask the student to state the purpose and describe the function of the program, and answers written early, at the design stage, tend to be sharper than answers reconstructed from finished code. When the purpose is crisp, design decisions gain a standard to answer to: a feature belongs if it serves the purpose, and it is decoration if it does not.

Input deserves the same precision. Input can arrive from a user typing, clicking, or selecting; from a file or data set the program reads; from a sensor or event in an environment that supports them. Whatever its source, input must matter: the program's behavior or output should change when the input changes, or the input is theater. A quiz whose questions never depend on the player's answers, or a calculator that ignores its second number, fails this test in ways readers notice quickly. Designing two or three contrasting inputs and predicting the outputs for each is a small exercise that exposes hollow input before it hardens into the final build.

Output is the program's answer back to the world: text on a screen, a drawing, a sound, a changed display, a computed result, a generated artifact. Output should be legible enough that a viewer of the video can tell what the program produced and whether it matches the input given. Programs whose output is a single number invite thin demonstrations, while programs whose output unfolds visibly, a filtered list appearing, a board updating, a summary taking shape, give the video natural material. Output design is therefore partly a scoring decision, since evidence the reader can see outperforms evidence the reader must take on faith.

Development process matters even though only the product is submitted. Students build the program incrementally during class sessions, and the guidelines expect development to happen across that window rather than in a single heroic sitting. Incremental building is also simply good engineering: get a small piece running, test it, add the next piece, test again. A program assembled in layers can be debugged layer by layer, while a program written in one untested mass hides its errors in crowds. Teachers watching the process will also see authorship happening in the open, which quietly supports the originality the task demands.

One more relationship is worth settling here, because students confuse the two computer science courses often enough that the comparison earns its own article in this series. AP Computer Science A centers on Java and on the end-of-course exam alone, while AP Computer Science Principles ranges across the field's big ideas and includes this performance task as part of the course's assessment. The comparison at [AP CSA versus AP CSP](/2008/06/03/ap-csa-vs-csp/) lays out the differences in content, language, and structure for students choosing between them or taking both. For Create Task purposes, the practical point is that CSP judges the design and explanation of a program in any language, which frees the student to build where they are strongest.

### How does a program show its purpose while it runs?

Purpose shows itself when a viewer can watch input change the output in a way that matches the stated goal. A planner that accepts a date and returns the day organized, a quiz that accepts an answer and responds to its correctness, each demonstrates purpose through behavior rather than through claims.

## Lists and the Work of Data Abstraction

Of the structures inside the program, the list carries the heaviest explanatory burden, because the written responses devote a full prompt to it. A list in this context is any structure that stores a collection of values under one name: an array, a list type, or an equivalent provided by the student's language or environment. Data abstraction means managing that collection as a single idea, so the rest of the program can think in terms of the whole group rather than juggling dozens of separately named variables. The responses ask the student to identify the list, explain what it represents, and show how using it helps manage the program's complexity. That trio of demands shapes how the list should be designed from the start.

The contrast that makes abstraction vivid is the variable explosion it prevents. Imagine a quiz built without a list: question one in one variable, its answer in another, question two and its answer in a third and fourth, onward through the whole bank. Every new question demands new names, new display code, new checking code. Adding a question means editing the program in many places, and the code swells while saying very little. The same quiz built on a list of questions treats each entry uniformly: display pulls the next item, checking compares against the stored answer, and adding fifty questions changes the data rather than the logic. That difference, felt in the fingers while coding, is exactly what the response prompt wants described in words.

Choosing what the list holds is a design decision with scoring consequences. Strong choices capture the program's central material: the tasks in a planner, the recordings in a practice log, the cells in a simulation grid, the entries in a collection tracker, the words in a generator's bank. Weak choices capture something peripheral, a list of menu labels, a list of colors used once, a list the code fills and never reads. The test is usage. Code should traverse the list, search it, filter it, sort it, add to it, remove from it, or compute across it, ideally in more than one of those ways, because the response must explain how the list manages complexity and a list the program barely touches gives the student little to explain.

Representation choices inside the list repay thought as well. Some programs store simple values; others store pairs or records, a question with its answer, an entry with its date, a product with its price. Parallel lists, where one list holds names and another holds corresponding scores, are a classic pattern in introductory environments and can serve perfectly well when the correspondence stays disciplined. Where the language offers records or objects, grouping fields together usually reads better and breaks less often. Either way, the student should be able to say what one element means, how the code finds elements it needs, and what would go wrong if the data grew tenfold.

Edge cases reveal whether a list design is honest. Empty collections happen: a planner with no entries yet, a search with no matches, a log on its first day. Code that assumes at least one element will crash or misbehave exactly when a demonstration reaches for an interesting case. Duplicate entries test whether the program treats them as legitimate data or as corruption. Growth tests whether loops, rather than hand written repetitions, do the processing, since a loop over a list scales while copied code blocks do not. Handling even one or two of these cases visibly, and mentioning the handling in the responses, signals the maturity readers reward.

Students often ask how large a list must be, and the honest answer is that size matters less than role. A list of eight elements that the program searches, filters, and summarizes does more for the submission than a list of eight hundred elements loaded and displayed unchanged. The written response succeeds when it can narrate a before and after: without the list, the program would need some painful alternative; with the list, a whole class of operations becomes uniform and short. Design the list so that story is true, and the prompt about data abstraction turns from an interrogation into a retelling.

Documentation habits formed here pay off later in the process. Naming the list after what it holds, rather than after its type, makes the code read like the response will sound. A comment where the list is created, stating what each element represents, becomes a draft sentence for the writeup. Keeping the list's creation, its population with data, and its main uses easy to locate matters practically, because the student will need to point readers at the relevant code segments and to discuss precisely how those segments behave.

## Procedures and the Work of Procedural Abstraction

Procedural abstraction is the second named idea in the responses, and it concerns the procedures a student writes: named blocks of code, defined once, that perform a specific job and can be called wherever that job is needed. A procedure might display the current state of a game, validate an entry, compute a summary, or advance a simulation by one step. The response prompt asks the student to identify a procedure they developed, describe what it does, and explain how it contributes to the program's overall function and how it manages complexity. As with the list, the design goal is a procedure with a real story to tell.

The natural test for a procedure is repetition with variation. When the same job appears in several places, or when a job is intricate enough to deserve isolation, a procedure earns its existence. Parameters make the abstraction genuine: a procedure that searches accepts the target as a parameter, a procedure that displays accepts the data to display, a procedure that scores accepts the answers being scored. Return values, where the language supports them, let a procedure hand results back cleanly. A procedure with no parameters that merely wraps three lines the program calls once is abstraction in costume only, and readers distinguish costume from substance by asking what would break, or duplicate, if the procedure were inlined everywhere.

Decomposition is the design habit underneath the concept. Building a program as a set of procedures means deciding where one job ends and another begins, which is the same judgment professional programmers exercise daily. A healthy structure for a Create Task program often shows a main flow that reads almost like the purpose statement, calling procedures whose names carry the meaning: set up the data, take the input, process the round, update the display, summarize the results. When the main flow reads that cleanly, the student can explain the whole program's architecture in the responses without inventing a story the code does not support.

Interaction between the procedure and the list is where many strong submissions shine. A procedure that receives the list, or works on the program's central list, and performs the filtering, searching, or transforming that the program exists to do, sits at the heart of the design. The algorithm the student features will often live inside such a procedure, which is convenient rather than coincidental: the response about the procedure and the response about the algorithm can point to related code while still answering different questions. One asks how the program is organized; the other asks how a particular computation unfolds step by step.

Refactoring deserves a mention, because first drafts rarely place the boundaries correctly. A student may build the program as one long sequence, get it working, and then notice that a block of code repeats with small differences. Extracting that block into a procedure with parameters is a normal, honorable stage of development, and it often produces the cleanest abstraction in the submission precisely because real use shaped it. The window allows this kind of revision when the schedule protects time for it, which is one more reason the planning section of this guide insists on finishing a working core before the final sessions.

Explaining a procedure well follows a pattern the student can rehearse. Name the procedure and state its job in one sentence. Describe its inputs, whether parameters, the central list, or values it reads, and describe what it produces or changes. Then make the complexity claim concrete: before the procedure existed, the program repeated this logic or tangled it into the main flow; with the procedure, the logic lives in one place, can be tested in isolation, and can be trusted by every caller. A response that walks those steps against a genuinely central procedure satisfies the prompt with room to spare.

## State, Variables, and the Discipline of Naming

Beneath the three featured structures sits a quieter layer of craft: how the program holds its state and what its pieces are called. State means the values the program remembers as it runs: the contents of the list, the score so far, the current round, the musician's chosen focus. Every input changes some part of that state, and every output reports on it. Students who can describe their program's state at any moment, which values exist, what each one means, and which code is allowed to change it, understand their program in a way that shows up unmistakably in the written responses.

Naming is where that understanding becomes visible on the page. A variable called by its meaning, sessionsTotal or nextSkill, explains itself to a reader and to the author returning after days away. A variable called x or temp2 explains nothing and forces every reader, including the future author, to reconstruct its purpose from context each time it appears. The same discipline applies to procedures: a name that states the job, recordSession or recommendNext, turns the main flow into a readable outline of the program's logic. Readers form judgments about code quality partly from these signals, and students form understanding by producing them.

Scope questions follow naturally. Some values belong to the whole program's life; others exist only inside one procedure's work. Keeping a value local to the procedure that uses it protects the rest of the program from accidental interference and makes the procedure testable on its own. Letting everything live globally feels easier for a week and then becomes the reason a change in one corner corrupts an unrelated corner. The featured procedure offers a natural place to practice the discipline: its parameters carry in what it needs, its local variables hold its scratch work, and its result returns cleanly to the caller.

None of this craft is separately scored, yet it underwrites everything that is. The list explanation reads better when the list has a meaningful name. The procedure explanation nearly writes itself when the procedure's name, parameters, and locals already tell the story. Even debugging accelerates, because a misbehaving value with a meaningful name announces which part of the state has gone wrong. Treating naming and state as design decisions rather than as typing is one of the habits that separates programs built for the task from programs merely assembled for it.

## The Algorithm at the Center

The third named idea is the algorithm, and the requirement has a specific shape: the student must identify and explain an algorithm inside the program that uses sequencing, selection, and iteration in combination. Sequencing is the ordered execution of steps. Selection is branching, where conditions choose which steps run. Iteration is repetition, where a loop carries steps around again. Nearly every program contains each ingredient somewhere; the requirement is stricter and more interesting than that. The featured algorithm must weave all three together inside one coherent computation, and that computation must matter to the program's purpose rather than decorate its edges.

A filtering algorithm shows the weave clearly. Suppose a study log program must display only the sessions that meet a student's chosen criteria. The computation proceeds in order: read the stored sessions, examine each one in turn, compare its attributes against the criteria, collect the matches, and present them. Iteration carries the examination across the whole list. Selection decides, for each session, whether it joins the results. Sequencing gives the whole thing its shape from first step to last. A student can narrate that algorithm in plain language, trace it by hand on sample data, and predict its behavior on edge cases, which is precisely the fluency the response prompt rewards.

Placement matters when choosing which algorithm to feature. The strongest candidate usually sits inside, or overlaps, the program's central procedure and operates on the central list, because centrality guarantees the algorithm is load bearing: remove it and the program stops fulfilling its purpose. Peripheral computations, computing a decorative average, formatting a label, blinking a cursor, may technically combine the three ingredients while saying nothing about the program. Readers weigh purpose, so the student should pick the computation whose absence would be felt immediately and explain it with the confidence of someone describing the engine rather than the paint.

Iteration inside the algorithm should be genuine repetition over data or conditions, not a loop that runs a fixed trivial count for show. Loops that traverse a list, search until a match appears, repeat until input validates, or advance a simulation until a stopping rule fires all demonstrate iteration with intent. Selection should likewise branch on conditions that arise from the data, varied enough that different runs take different paths. An algorithm whose branch always resolves the same way on every realistic input is a sequence wearing a costume, and tracing the algorithm on two contrasting examples is a reliable way to detect the costume before a reader does.

Tracing deserves emphasis as a study and writing technique. To trace is to follow the algorithm on paper with concrete values, recording how variables and collections change at each step. A student who has traced the featured algorithm twice, once on ordinary data and once on a case that exercises the other branch or the loop's exit, can write the response from knowledge rather than hope. The trace also tends to expose bugs: an off by one boundary, a condition inverted, a result collected but never used. Finding those in the middle sessions, while repair time remains, is the difference between an algorithm that is explained and an algorithm that is merely asserted.

The response about the algorithm asks for explanation at two levels: what the algorithm accomplishes within the program, and how its code implements that accomplishment using the three ingredients. Strong answers keep the levels connected, naming the step in the code for each claim in the summary. Weak answers summarize a goal the code only approximates, or paste a tour of lines without saying what they achieve together. The design implication repeats the series thesis of this guide: choose and build the algorithm early enough that it is genuinely central, and the explanation becomes a description of something real.

### Where do strong projects quietly lose ground?

Ground disappears in the gaps between artifacts: a program feature the video never shows, a response describing code that was later rewritten, a list explained as central while the program barely touches it. Quiet cross checking, artifact against artifact, catches those gaps while repair is still cheap.

## Selection and Iteration in Practice

Because the featured algorithm must combine sequencing, selection, and iteration, each ingredient deserves a closer look at the level where students actually write code. Selection first. A branch is a question the program asks its data: does this session meet the criteria, is the list empty, has the player answered correctly, does the requested item exist? Well built branches partition the possibilities cleanly, so every realistic case lands somewhere intended and no case falls through a crack between conditions. The classic student errors are branches that overlap, branches that leave a gap, and conditions that test a different variable than the author believes. Tracing two cases that should take different paths exposes all three errors within minutes.

Compound conditions deepen selection's power and its risk. Combining tests with and, or, and not lets a program express rules like recommending a skill that is both neglected and not practiced yesterday. Each added clause narrows or widens the set of cases that pass, and the author must be able to say, for any concrete case, exactly which clauses decided its fate. A reliable design habit is to build the condition in layers: test the simple disqualifiers first, then the qualifying evidence, in the order a person explaining the rule aloud would use. Code shaped like its own explanation is code the written response can describe without strain.

Iteration has its own anatomy. Every loop needs an initialization that sets up its progress, a condition that decides whether another pass happens, and an update that moves the work forward. Loops over lists usually follow the traversal pattern, visiting each element once to examine, count, collect, or transform it. Search loops add an exit when the target appears. Accumulation loops carry a running total or a growing result collection across passes, and their correctness lives in the details: the total starts at the right value, each pass adds exactly the elements that qualify, and nothing is counted twice. Off by one errors, where a traversal skips the first or last element or a boundary case slips past the condition, are the most common genuine bugs in student algorithms and the easiest to catch with a three element trace.

Nested structures are where the combination the task requires becomes unmistakable. A loop that traverses the list while a branch inside decides each element's treatment is already the skeleton of countless real algorithms. A branch that chooses between two different loops expresses a program with modes. A loop inside a procedure called from several places multiplies the structure's reach. Students do not need baroque nesting to satisfy the requirement; one honest loop with one meaningful branch inside it, operating on the program's real data, demonstrates the combination more convincingly than a thicket built for show. The response should be able to point at the loop, name the branch, and describe the sequence that contains them both.

Sequencing, the plainest ingredient, still rewards attention. The order of steps inside an algorithm encodes assumptions: validate before storing, compute before displaying, update the list before summarizing from it. Reordering steps that look interchangeable is a classic source of bugs that appear only on the second run or the second round, when state left by the earlier pass meets assumptions written for a fresh start. When a student explains the featured algorithm, narrating the order and one reason for it, the explanation signals a designer rather than a transcriber, and that signal is part of what the scoring rows are listening for.

## The Video: Proof the Program Runs

The video exists to answer a reader's simplest question: does this program actually do what its author says? Within its short span, the recording should show the program receiving input and producing the corresponding output, traveling the main path of the program's purpose. Viewers should be able to see the input happen, not just hear it described, and should see the output arrive as a consequence. A demonstration that shows only a title screen, or that talks over a static display, leaves the central question unanswered no matter how polished the narration sounds.

Choosing what to demonstrate is an editorial decision. The main path comes first: the interaction a typical user would have, from launch to result. If time allows, one variation strengthens the proof, a second input that takes a different branch, a search that finds nothing, a round played badly instead of well, because contrast shows the program responding rather than replaying. What the demonstration should avoid is a tour of every corner; depth on the central path persuades more than breadth across decorations. Planning the demonstration against the written responses is wise, since the responses describe behavior the video ideally makes visible.

Rehearsal separates credible recordings from fumbled ones. A student should run the exact demonstration at least twice before recording: same inputs, same order, same pauses. Rehearsal exposes practical hazards, a mistyped entry that derails the flow, a window sized so the output hides off screen, a step that takes long enough to feel broken. It also builds the calm familiarity that lets a narrator speak about what is happening rather than merely keep up with it. Recording early enough to allow a retake is part of rehearsal's value; a video captured in the final minutes of the window carries whatever accidents happened to occur.

Narration and clarity deserve care within the limits the guidelines set for the recording. The screen should show the program large enough to read, the cursor or hands should move deliberately, and any spoken or captioned explanation should name the input being given and the output expected. Students whose programs produce sound, animation, or rapid change should slow the demonstration down, repeating a key moment if needed, because a reader watching once cannot rewind a blur into evidence. The goal is not production glamour. The goal is that a stranger, watching a single time, finishes convinced the program works as claimed.

Technical housekeeping protects the effort. Save the recording where the submission process expects it, verify the file plays from start to finish on a machine other than the one that made it if possible, and confirm the program shown in the video is the same version as the program submitted. Version drift, where the code kept evolving after the recording, is a quiet source of contradiction between artifacts: the responses describe one behavior, the code implements another, the video shows a third. Freezing the program before recording, and changing nothing afterward except through a deliberate recheck of all three artifacts, prevents the drift entirely.

## The Written Responses: Where the Score Is Argued

Every misconception about the Create Task eventually reduces to one error: treating the written responses as paperwork that follows the real work. The scoring structure disagrees. The program and the video establish what exists; the responses establish what the student understands about what exists, and understanding is what the course certifies. A reader cannot interview the author, cannot watch over their shoulder during development, and cannot infer intentions from uncommented code with any confidence. The responses are the author's testimony, and testimony presented carelessly loses cases that evidence alone might have won.

Consider what each response must accomplish. One response states the program's purpose and describes its function, connecting what the program is for with what it observably does. Another turns to the list and asks the student to explain the data abstraction: what the collection represents, what the program does with it, and how it helps manage complexity. A third turns to the chosen procedure and asks for the same treatment of procedural abstraction. A fourth examines the featured algorithm and asks how sequencing, selection, and iteration combine within it. Across the four, the pattern is constant: identify the code, describe its behavior, and explain its contribution. Students who internalize that pattern early write responses that feel less like an exam and more like a design review.

Specificity is the currency these responses trade in. General truths about programming earn little, because they could be written about anyone's code. Statements anchored to the submission earn credit: the name of the actual list, the actual values it holds, the actual procedure and its parameters, the actual conditions the algorithm tests and the loop it repeats. A useful self test is substitution: if a sentence from a response could be pasted unchanged into a classmate's submission and remain true, the sentence is probably too general to help. Rewriting until every sentence fails that substitution test, until each one belongs to this program alone, produces responses with the density readers reward.

Accuracy between the responses and the code is the second currency. Claims must match the submitted program as it stands, line for line in spirit. A response that describes a validation step the code performs only sometimes, or credits the list with processing the code actually does by hand, creates a contradiction a careful reader will find. That is why the responses should be written or revised against the final code, with the source open beside the writing. It is also why freezing the code before the final writing pass, the same discipline the video demands, protects the whole submission from drift.

Drafting the responses alongside development, rather than after it, changes their quality in a way students consistently underestimate. A sentence written while a design decision is fresh carries the reasoning with it: why the list stores pairs instead of single values, why the procedure takes the round's data as a parameter, why the loop tests its condition where it does. Reconstructed weeks later, the same decisions may be honestly unrecoverable, and the response fills with plausible invention that the code contradicts in detail. Keeping a running design journal, even a few lines per session recording what was built and why, gives the final writing a memory to draw on.

Voice and clarity matter more than ornament. The responses are technical explanations, and their ideal style is the style of a good comment grown longer: plain words, precise terms used correctly, sentences that say one thing each. Terms from the course, abstraction, parameter, iteration, selection, should appear where they genuinely apply, because correct vocabulary signals the understanding being scored, while vocabulary sprinkled for decoration signals the opposite. Length limits in the guidelines reward economy as well; a response that answers fully in fewer words beats one that pads toward a ceiling, since padding dilutes the specific claims readers are scanning for.

A concrete way to prepare is to rehearse the four explanations aloud before writing them. Explain the purpose to an imaginary classmate in two sentences. Explain the list: what it holds, what the code does with it, what life without it would look like. Explain the procedure the same way. Then walk the algorithm on a small example, naming each decision and each repetition as it fires. Anything that cannot be said aloud smoothly will not write smoothly either, and gaps discovered in rehearsal can still be closed in code. Gaps discovered while staring at a blank response box, with the window nearly closed, mostly get papered over, and papering is what readers are trained to detect.

One more consideration links the responses back to the rest of the course. The end-of-course exam still awaits, and it draws on the same concepts: data, algorithms, programming, and the impact of computing. The explanation skills practiced here, describing an algorithm precisely, reasoning about a list's contents, predicting a procedure's effect, are exam skills wearing work clothes. Students preparing for the multiple choice portion can sharpen the same instincts with [multiple-choice strategies that apply across AP subjects](/2006/10/27/ap-multiple-choice-strategies-all-subjects/), and those returning to refresh course concepts will find [free AP math and science practice questions](https://reportmedic.org/tools/ap-math-science-practice.html) useful for keeping the underlying ideas in shape while the project matures.

## Inside the Four Responses: A Closer Reading

The response about purpose and function sets the terms for everything after it. Purpose names the problem or the opportunity the program addresses and the user it serves; function describes what the program does when it runs, in terms of inputs accepted and outputs produced. Strong versions keep the two ideas distinct, because a program can be described functionally all day, screens, buttons, totals, without ever saying why anyone would want it, and can be praised purposefully without revealing a single behavior. The reader is looking for the handshake between the two: this program exists to do this, for this person, and here is the behavior that accomplishes it.

Precision about the user sharpens both halves. A practice companion for musicians preparing auditions has a different purpose from a general habit tracker, even if the code shares bones, because the decisions inside, what counts as neglect, what summary matters, follow from the specific user. Students who chose their idea from genuine interest usually have this precision for free and simply need to write it down. Students who chose an abstract idea discover, in this response, whether an actual user was ever imagined, and the discovery sometimes sends them back to the design with a better question than any the code had posed.

The list response succeeds on the strength of its complexity argument. Identifying the collection and stating what it stores earns the opening ground; the credit deepens when the student explains what the program does with the stored data and what the code would look like without the abstraction. The strongest versions quantify the contrast informally: entries handled by one loop rather than by repeated blocks, new data absorbed by changing the list's contents rather than the program's logic, a search expressed once and used everywhere. Weak versions describe the list as a container and stop, as though storage itself were the achievement, when storage is merely the premise and management is the achievement.

The procedure response turns on contribution. A strong answer names the procedure, states its job, identifies its parameters and what it returns or changes, and then argues for its necessity: the program calls it from these places, for these reasons, and the alternative, duplicating its logic at every call site, would tangle the program and multiply the places a fix must be applied. The argument is the same argument a professional makes when defending a design in review. Weak versions summarize the procedure's lines without establishing why the program is better for having it, leaving the reader to wonder whether the procedure is an abstraction or a detour.

The algorithm response is the most technical of the four and rewards the tracing habit most directly. A strong answer describes the computation's goal, walks its steps in order, points out where the branch examines the data and decides, and where the loop carries the work across the collection or toward its stopping condition. It often includes a miniature example, three elements and two outcomes, showing the algorithm thinking. Weak versions list the ingredients, sequence here, selection there, iteration in the corner, without showing them combined in a single working computation, which is rather like listing flour, water, and heat without mentioning bread.

Across all four, one discipline unifies the strong answers: every claim names its evidence. The response writer who habitually writes "the list, which stores each session as a date, a skill, and a rating" is doing more than being thorough; they are making the reader's verification effortless. Responses written to that standard also tend to be shorter than anxious ones, because evidence is compact while reassurance is bulky. Students drafting their final versions can use that as a late editing rule: cut any sentence that reassures, keep every sentence that shows.

## Talking About Code: Vocabulary That Works

Written responses live or die on the precision of their terms, and a handful of words do most of the work. A parameter is the named input a procedure declares; an argument is the actual value passed when the procedure is called, and keeping the pair straight lets a student describe data flow exactly. A return value is what a procedure hands back to its caller. A condition is the test inside a branch. A traversal is a pass through a collection that visits its elements. State is the set of values the program remembers. Used correctly, these words compress paragraphs of vague description into sentences a reader can verify against the code.

Abstraction itself has levels worth distinguishing in prose. Data abstraction hides the details of how a collection is stored so the program can work with the collection as an idea. Procedural abstraction hides the details of how a job is done so callers can use the job by name. Both are forms of managing complexity, the phrase the prompts return to, and the strongest responses make the management concrete: this detail is hidden, this caller is spared, this change can be made in one place. A student who can point at what is hidden, not merely assert that something is, has understood the concept at the depth the course intends.

Verbs matter as much as nouns. Code reads, stores, compares, accumulates, filters, selects, returns, repeats, and terminates, and responses built from those verbs track behavior faithfully. Vague verbs, handles, deals with, does, hide the very mechanics the reader is scoring. A useful drafting exercise is to search a draft response for its verbs and replace every vague one with the specific action the code performs. The exercise takes minutes and reliably raises the response's evidentiary density, which is the quality every scoring row is ultimately measuring.

## The InsightCrunch Create Task Checklist

Guides persuade; checklists verify. The InsightCrunch Create task checklist compresses this article into a sequence a student can work through from idea to submission, checking each stage before trusting the next. Read it as a set of gates rather than as advice. A stage is not finished when it feels finished; it is finished when its check can be answered yes with evidence in hand. Students who pin the checklist beside their workspace and mark stages off in pencil tend to discover their problems in the order the problems are cheapest to fix.

| Stage | What to produce | Check before moving on |
| --- | --- | --- |
| Idea | A one sentence purpose with a named user and benefit | The idea fits the window with features that can be cut |
| Design sketch | Inputs, outputs, and the data the program will hold | Every requirement has a visible home in the sketch |
| List design | The central collection and what one element means | Code will search, filter, sort, or summarize the list |
| Procedure design | The main procedure with its parameters named | Removing it would force repeated logic across the program |
| Algorithm design | The featured computation described in plain steps | Sequencing, selection, and iteration all appear inside it |
| Working core | The smallest program that fulfills the purpose | It runs end to end on ordinary input without crashing |
| Test pass | Contrasting inputs, edge cases, and a hand trace | Behavior matches predictions, including empty data |
| Video | A rehearsed recording of input becoming output | The file plays cleanly and shows the submitted version |
| Written responses | Four explanations tied to the final code | Every claim matches the program line for line in spirit |
| Final review | A cross check of program, video, and responses | No artifact contradicts another, and credits are complete |

Two habits make the checklist more than wall decoration. First, revisit it at the start of every session rather than only at milestones, because a stage quietly reopened by a design change, a list repurposed, a procedure split in two, needs its check repeated. Second, treat a failed check as scheduling information rather than as a verdict. A failed check in the middle of the window is the system working; the same failure surfacing during the final review is the system arriving late. The checklist cannot supply judgment, but it can make sure judgment gets applied while options remain open.

### Why write the responses alongside the code instead of afterward?

Decisions are easiest to explain while their reasons are still warm. A list shaped on Tuesday gets its rationale recorded on Tuesday, in words the final writing can borrow. Postponed explanations must be reconstructed from silent code, and reconstruction invents details that careful readers catch. Writing alongside also exposes design gaps early.

## Before the Window Opens: Preparation That Pays

Although the program itself must be developed during the designated sessions, nothing prevents a student from arriving at those sessions prepared, and preparation is where much of the score separation quietly happens. The most valuable preparation is fluency in the environment: knowing how to create and traverse a list, define a procedure with parameters, write a loop with a clean exit, and read input without consulting notes. These are course skills the student has presumably been building all year, and the weeks before the window are the time to shore up whichever of them feels shakiest, using ordinary coursework and practice rather than any work on the task itself.

Small rehearsal programs, built as coursework, are the standard way to build that fluency honestly. A tiny program that stores five items in a list and prints the largest teaches the traversal pattern in an hour. A miniature quiz with three questions teaches the round procedure. A toy simulation with a handful of agents teaches the step loop. None of these is the Create Task, and none should be submitted as it, but each one converts a concept the student can recognize into a pattern the student can produce under time pressure, which is the exact conversion the window rewards.

Reading rounds out the preparation. The course framework and the task's guidelines, read before the window opens, turn the first design session into a confirmation exercise rather than an orientation. Students who have read the requirements in the source can spend their opening sessions designing against them, while students meeting the requirements for the first time spend those sessions absorbing information that was always available. Teachers differ in how they stage the introduction, and local instructions govern, but the principle survives every staging: the earlier the requirements are understood, the more of the window remains for building.

Idea incubation is the softest form of preparation and the one most easily abused, so its boundary deserves a sentence. Thinking about possible projects, noticing problems in daily life a program could address, and arriving with candidate ideas is healthy and human. Developing the actual program, its code, its video, or its written responses outside the designated process is not preparation but a rules violation, and the distinction is one teachers can clarify for any student unsure where a particular activity falls. Preparation aims at readiness, not at a head start on the artifact.

## Planning the Work Inside the Window

The window is the task's quiet antagonist. The College Board frames the Create Task as work done during designated class time, and the teacher administers the schedule, so the student experiences the task as a sequence of sessions with hard edges: bells ring, other courses call, and the program must advance in the intervals given. Planning inside such a window differs from planning an open ended project. Every session needs an entry state, a goal sized to the period, and an exit state that the next session can resume without archaeology. Students who plan at that granularity rarely lose whole sessions to remembering where they were.

A sound session plan distributes the work in a deliberate order. Early sessions belong to design: the purpose sentence, the sketch, the list, the procedure, the algorithm on paper. Middle sessions belong to building the working core, the smallest program that fulfills the purpose, then layering the features that make it complete. Late sessions belong to testing, recording, and writing, in that order, because each depends on the stability of the one before. The most common planning failure is a schedule that spends nearly every session building and leaves the video and responses to share whatever time remains, which is how strong programs end up argued by weak submissions.

Buffer is the difference between a plan and a hope. Experienced builders assume some sessions will be lost to confusion, environment trouble, or a bug with a long tail, and they schedule as if the window were shorter than it is. A student who aims to finish the working core with a third of the window still in reserve can absorb a bad week; a student whose plan requires every session to go well has built a plan that reality will edit without permission. Cutting scope early, when a feature proves stubborn, is the companion skill: a smaller finished program outscores a larger unfinished one in every row the readers apply.

Version discipline keeps the plan honest. Save the program at the end of every session under a name or number that shows its place in the sequence, and keep the earlier versions rather than overwriting them. When a change breaks something that worked, the previous version is both a refuge and a diagnostic tool, and comparing the two often names the bug faster than staring at the broken one. The habit also documents development across the window in the most natural way possible, a trail of artifacts showing the program growing under the student's own hand.

Session notes deserve the same discipline. Two or three lines at the end of each session, recording what changed, what works, what remains, and what decision is pending, cost almost nothing and repay themselves at the start of the next meeting. Those notes double as the design journal the writing section of this guide recommends, because decisions captured in the moment become explanations later. A student who can read, in their own words, why the list changed shape in the third session writes that response with an authority no amount of last minute staring at code can reproduce.

Teachers administer the window, and wise students use them within the rules. A teacher can clarify the task's requirements, explain course concepts, and help with the logistics of the environment, and asking about a confusing requirement early is professionalism rather than weakness. What a teacher cannot do is design the program or draft the responses, and the line between guidance and authorship is one the guidelines draw carefully. Knowing where that line sits, and staying visibly on the right side of it, is part of the originality discipline covered later in this guide.

Finally, plan for the end at the beginning. The last session should be reserved for verification only: playing the video, rereading the responses against the code, confirming the credits, and checking the files. Nothing new should be built there, because anything built there cannot be tested, filmed, and written about with care. A schedule that protects a pure verification session at the end, and treats it as untouchable even when a tempting feature beckons, is the single clearest marker of a student who has understood what kind of task this is.

## A Session-by-Session Walkthrough

Plans become real when they are laid against the calendar of an actual window, so consider how the work distributes itself across a representative sequence of sessions. The opening sessions belong to thought rather than code. The student settles the purpose sentence, interviews the idea against the scope tests, and produces the design sketch with its inputs, outputs, list, procedure, and algorithm described in words. A session journal opens here, and the first response drafts, purpose and function at least, can be sketched while the design is being argued about, because the design conversation and the response are the same conversation held at different volumes.

The next block of sessions builds the spine. The student creates the list with sample data, writes the procedure that adds to it, and gets input flowing in and output flowing out in the plainest possible form. Nothing decorative happens here, and the discipline is the point: a program whose spine runs end to end, however roughly, can be improved along every dimension, while a program that exists as polished fragments cannot yet do anything. Testing begins in this block, not after it, with predictions recorded for the spine's main path and the first hand trace of the algorithm sketched on paper beside the keyboard.

The middle sessions deepen the core. The featured algorithm grows its real branches, the procedure gains its parameters and its second caller, edge cases like empty data get their handling, and the responses gain their second and third drafts as the code gives them more to describe. This is also where scope decisions bite: the checklist gets reviewed, the decorative features get ranked, and the first honest conversation happens about what will be cut if the remaining sessions shrink. Students often experience this block as the least visible progress, because the program looks similar while becoming substantially more correct. The journal tells the truer story.

The closing sessions convert the program into a submission. Testing turns adversarial, hunting the inputs most likely to embarrass the demonstration. The code freezes except for repairs. The video is rehearsed and recorded with time reserved for a second attempt. The responses are finalized against the frozen code, claim by claim. And the final session is reserved, as the planning section insists, for verification alone. Viewed from the end, the walkthrough's shape is a funnel: wide exploration early, narrowing commitments in the middle, and a disciplined conversion of finished work into scored artifacts at the close.

## Testing and Debugging as a Scored Habit

Only the finished artifacts are submitted, yet testing shapes the score through every channel available to it. The video can only show behavior that works. The responses can only describe an algorithm the student actually understands, and tracing during testing is where that understanding forms. Even the program's design improves under testing pressure, because features that resist testing tend to be features built on confusion. A student who tests early and continuously is therefore not polishing a finished thing; they are manufacturing the evidence the rest of the submission will present.

Useful testing begins with prediction. Choose an input, state what the program should do with it, then run and compare. When prediction and behavior agree, the test confirms understanding; when they diverge, the divergence is a lesson about either the code or the mental model, and both are worth having. Inputs should vary along the dimensions the program claims to handle: ordinary values in the middle of the range, values at the boundaries, values just outside them, and the awkward cases, empty input, repeated input, input in an unexpected order. A program that survives its author's deliberate attempts to embarrass it will survive a reader's demonstration path.

The featured algorithm deserves its own testing ritual, the hand trace described in the algorithm section. Trace on paper with a tiny data set, three or four elements, chosen so the loop repeats more than once and the branch resolves both ways across the run. Record the state after each pass: which element is under examination, what the condition found, what changed. When the trace and the program agree, the student owns the algorithm in the only sense the responses can certify. When they disagree, the student has found either a bug or a misunderstanding, each cheaper now than during the writing.

Debugging method matters as much as debugging effort. Change one thing at a time, and retest after each change, so cause and effect stay linked. Shrink the failing case until it is the smallest input that still fails, because small failures have fewer places to hide. Read the code that actually ran rather than the code the author believes they wrote; inserting temporary output that reports variable values during a run turns invisible state into evidence. These habits are course content in their own right, and exercising them during the task consolidates exactly the skills the end-of-course exam will probe afterward.

Testing also protects the schedule. Bugs found in the middle sessions are errands; bugs found during the recording session are crises. A program whose core path has been exercised daily rarely ambushes its author on camera. Students should therefore test the demonstrated path specifically, the exact inputs the video will show, until that path is boring. Boring is the goal: a demonstration that cannot surprise its presenter frees attention for narration, pacing, and the small courtesies that make a recording easy to follow.

Keeping a small, fixed set of test cases pays compound interest across the window. A student who saves the exact inputs used in early tests, together with the outputs a correct program should produce for them, owns a regression suite in everything but name. After any fix or refactor, rerunning those cases takes minutes and answers the only question that matters at that moment: did the change break anything that used to work? Programs evolve through dozens of small changes during the build, and each change is a fresh opportunity to damage an old behavior silently. The fixed set turns that silent damage into an immediate, visible mismatch.

Fresh eyes find what authorial eyes skip. Handing the program to a user who did not build it, a classmate acting purely as an audience member, surfaces assumptions the author no longer notices: an instruction only the author understands, an input format nothing announces, a button whose purpose is obvious only to its maker. Watching someone use the program without intervening is an education no amount of self testing reproduces, because the author cannot unknow the intended path. Notes from such a session, gathered without accepting any design or code from the tester, feed directly into clearer prompts, better labels, and a demonstration path a stranger can follow.

## A Worked Example: One Project from Sketch to Submission

Abstract advice hardens into skill when it is watched operating on a single concrete case. Consider a student, call her Mara, who plays in a school jazz band and builds her Create Task around a practice companion. Her purpose sentence reads: the program helps a musician structure practice by storing past sessions, recommending what to work on next based on what has been neglected, and summarizing the week. Notice what the sentence contains: a user, a benefit, and verbs the code can actually perform. It also quietly promises the required structures, because recommendations imply decisions, sessions imply a collection, and summaries imply computation across that collection.

Her design sketch names the pieces before any code exists. Input arrives as the details of a finished session: the date, the skill practiced, the minutes spent, and a self rating of how it went, plus a request when the musician asks what to practice next. Output appears as the recommendation, the updated session list, and a weekly summary. The central list stores sessions, each element holding those four fields together so a session travels through the program as one thing. A procedure named for its job will record a new session, validating entries and appending the record. The featured algorithm will produce the recommendation: it scans the stored sessions, totals recent minutes per skill, applies the musician's chosen focus rules, and selects the skill whose balance of neglect and importance argues loudest.

Building proceeds in the order the planning section prescribes. Mara first makes the smallest version that fulfills the purpose: sessions can be added, stored in the list, and printed back, with the recommendation computed by a rough rule. Only when that spine runs does she refine the algorithm, adding the branch that treats a skill practiced heavily on the previous day as ineligible for recommendation, and the loop exit that stops scanning once the list is exhausted. Each refinement gets tested against predictions she writes down before running, and two genuine bugs surface during those tests: a boundary error that drops the final session from the totals, and an inverted comparison that recommends the most practiced skill instead of the least. Both are the sort of error a hand trace exists to catch, and her trace catches the second one before the code does.

The list earns its response honestly in this design. Without it, every session would need its own set of variables, and the totals computation would repeat the same addition once per hard coded session, growing longer and more fragile with each addition. With the list, one loop serves any number of sessions, and adding a week of data changes nothing structural. Mara's response can say exactly that, pointing at the procedure that appends sessions and the algorithm that reads them. Her procedural abstraction has an equally concrete story: the recording procedure is called from the entry flow and from a correction flow that fixes a mistyped session, so its logic lives in one place, tested once, trusted twice.

The video practically directs itself once the program is stable. Mara rehearses a demonstration in which she adds two sessions with contrasting ratings, asks for a recommendation, and shows the program choosing the neglected skill her trace predicted, then requests the weekly summary and watches it reflect the entries just added. Because the demonstration uses the same contrasting inputs as her testing, nothing on camera can surprise her. Her responses, drafted from the session journal she kept while building, describe the same path the video shows and the same code the reader can inspect. The three artifacts corroborate one another, which is the deepest structural goal of the whole task.

Two features never made it into Mara's program, and their absence is part of the example's lesson. A calendar view and a streak celebration animation both fell to scope cuts when the boundary bug consumed a session she had reserved for decoration. The cuts hurt less than expected, because neither feature carried a requirement. The recommendation engine, the list, and the recording procedure, the parts the score actually examines, were already finished and tested. Planning had sorted the features into load bearing and decorative long before the crisis arrived, which is exactly the sorting a student wants done in advance.

## Choosing a Language and Environment

The task leaves the programming language open, and the freedom deserves a deliberate decision rather than a default. Classrooms build Create Task programs in block based environments designed for the course, in Python, in JavaScript, and in a range of other languages and tools. Scoring follows the ideas in the code, so the wisest choice is usually the environment where the student can already express lists, procedures, and loops without fighting the notation. Fluency beats prestige: a modest program written confidently in a familiar environment outscores an ambitious one abandoned mid window in an impressive language the student was still learning to spell.

Environments differ in how they support the required structures, and the differences are worth a session of exploration before committing. A list should be easy to create, extend, and traverse. Procedures should accept parameters without ceremony. Input and output should be visible enough to film. Some environments wrap these in friendly blocks; others expose them as text the student must type exactly. Neither style is inherently stronger, but a mismatch between the student's habits and the environment's demands taxes every session. Students who have spent the course in one environment possess a presumption in its favor that only a serious obstacle should overturn.

Portability and access belong in the decision as well. The program must be openable, runnable, and recordable during class sessions on the machines the school provides, and the student must be able to preserve versions between sessions without drama. An environment that lives on a personal device the school restricts, or behind an account the student cannot reach from the lab, converts every session into a negotiation. Boring reliability is a feature. The build sessions are scarce, and spending them on access problems rather than on the program is a tax no design can afford.

One further angle connects the choice to the rest of the student's AP portfolio. Students weighing the two computer science courses, or the broader set of quantitative subjects, sometimes let the Create Task's open language policy blur real differences in what each course examines. The series' [comparison of AP math options across Precalculus, Calculus, and Statistics](/2008/06/08/ap-math-comparison-precalc-calc-stats/) treats the mathematics side of that decision, and the CSA comparison cited earlier treats the computing side. For the Create Task itself, the principle stands alone: choose the environment that lets the required ideas show most clearly, then commit, because switching languages mid window spends the scarcest resource the task has, which is sessions.

## Input and Output Patterns Worth Borrowing

Certain input patterns recur across successful projects because they map cleanly onto the task's requirements. The entry pattern asks the user for a record, validates the pieces, and stores the result in the central list: a session logged, an expense entered, a sighting reported. Validation inside the entry pattern, rejecting an empty field or an impossible value and asking again, quietly demonstrates selection doing honest work. The query pattern runs the other direction: the user names a criterion, and the program searches or filters the list and presents what matches. Query patterns make iteration and selection visible on demand, which is why they serve the video so well.

The choice pattern drives games, quizzes, and branching tools: the program presents a state, the user chooses, and the program updates the state in response. Its design burden is the set of possible states and the rules that move among them, which the student must be able to enumerate and test. The configuration pattern opens simulations and generators: the user sets starting conditions, sizes, speeds, seed values, focuses, and then watches behavior unfold under those settings. Configuration input is easy to demonstrate dramatically, since two contrasting settings produce visibly different runs, and contrast is the video's best friend.

Output patterns deserve the same deliberation. The report pattern assembles a summary from the whole collection: totals, averages, extremes, the week's picture. Reports reward the accumulation loop and give the algorithm somewhere meaningful to land. The view pattern presents the collection itself, filtered or ordered by the user's query, so the audience sees the data the program manages rather than only conclusions drawn from it. The artifact pattern produces something the user keeps: a generated routine, a printable plan, a composed pattern, a recommended list. Artifact outputs make purpose tangible, since the program's benefit leaves the screen with the user.

Feedback is the pattern that ties input and output into a loop the user can feel. Immediate, specific feedback, the entry was saved, that answer was close, this skill has been neglected for six days, teaches the user the program's model of the world and invites the next input. Programs with thoughtful feedback demonstrate purpose better than programs that merely compute correctly in silence. When a student designs the demonstration for the video, the feedback moments are usually the beats worth slowing down for, because they show the program responding as a designed thing rather than executing as a mechanism.

Error handling is the pattern students most often omit and readers most quietly appreciate. Every input channel can receive nonsense: text where a number belongs, a date outside the program's range, a selection with nothing behind it. A program that anticipates the likeliest nonsense on its main paths, and responds with a correction request rather than a crash or a silent wrong answer, displays the maturity the course tries to build. Error cases also belong in testing, and one graceful recovery shown in the video can do more for a reader's confidence than three flawless ordinary runs.

## Comments, Credits, and Code from Elsewhere

Documentation inside the program serves two masters: the reader scoring the submission, and the student returning to the code after a weekend away. Comments placed where the list is created, where the main procedure begins, and where the featured algorithm turns its corners explain intent at exactly the points the written responses will discuss. A comment earns its place by saying something the code cannot say itself: why a threshold was chosen, what an element of the list represents, which real world rule a branch encodes. Comments that merely translate code into words, announcing that a loop loops or that a variable is being set, add noise and quietly lower a reader's confidence in the rest.

Professional programmers borrow constantly, and the Create Task does not pretend otherwise. A student may adapt a pattern from course materials, documentation, a tutorial, or another legitimate source, provided the borrowing is acknowledged. The acknowledgment belongs in the code near the borrowed material and should name what was taken, where it came from, and what the student changed. Precision matters: a credit that gestures vaguely at the internet protects nobody, while a credit that identifies the source and the extent of the adaptation demonstrates the scholarly honesty the task is testing alongside the programming.

The boundary the guidelines guard is authorship of the core. The list, the procedure, and the algorithm the responses describe must be the student's own design and implementation, because the responses claim them as evidence of the student's understanding. Borrowing a sorting routine for a decorative corner of the program, credited properly, is ordinary practice. Presenting a borrowed routine as the featured algorithm empties the corresponding response of meaning, since the student would be explaining decisions they did not make. The practical test is explainability: if the student cannot walk through a stretch of code decision by decision, that stretch must not carry weight in the submission, whatever its source.

Teachers occupy a defined place in this economy of help. They can explain concepts, clarify requirements, comment on whether a plan addresses the task, and assist with the environment's mechanics. Classmates can discuss the course's ideas in general terms. Neither may supply the design, the code, or the wording of responses for a student's submission. Students sometimes drift across these lines gradually, accepting one suggestion too many until the program is partly someone else's. The checklist habit helps here as well: at the final review, the student should be able to say of every load bearing part, this is mine, I can explain it, and I can change it without help.

Citations also protect the student. A program that grows across many sessions may absorb a snippet found during an evening search and half forget the absorption by the following week. Crediting at the moment of borrowing, while the source is still on screen, keeps the record accurate without effort. The session journal offers a natural place to log borrowings as they happen, with the source named. When the final review arrives, the credits in the code and the log can be compared, and gaps closed, before the submission goes out carrying the student's name.

## Scoring in Plain Terms

Scoring begins from a simple premise: readers award credit for evidence, and the submission is the only evidence they receive. Trained readers apply the College Board's scoring guidelines to the program, the video, and the written responses together, looking for the specific demonstrations the guidelines name. A requirement met visibly and described accurately earns its credit. A requirement met invisibly, present in the code but never surfaced in the responses or the demonstration, is a gamble. A requirement described but not actually present in the code is a contradiction, the weakest position of all.

The conceptual rows of the guidelines mirror the structure this guide has followed. Credit attaches to the program's purpose and function as described and demonstrated. Credit attaches to the data abstraction, where the student must show a list that stores data so the program's purpose can be achieved and explain how it manages complexity. Credit attaches to the procedural abstraction, where a student developed procedure must contribute to the program's function, with its behavior explained. Credit attaches to the algorithm, where sequencing, selection, and iteration combine in service of the purpose and the student explains how. Around those centerpieces sit expectations about input, output, and the program's overall development, all of them examinable in the artifacts.

Partial evidence earns partial standing in ways students should understand. A list that exists but barely participates in the program's work supports a weaker explanation than a list at the center. A procedure that is called once and takes no parameters shows less abstraction than one reused with arguments. An algorithm whose loop exists but whose branch never changes the outcome shows the ingredients without the combination. None of these is worthless, and a student short on time should absolutely submit the partial version rather than nothing. But the gradient explains where revision effort pays: strengthening the weakest of the core structures usually buys more than decorating the strongest.

Reading the guidelines directly is an underused advantage. They are written for readers, which means they describe, in plain operational language, what earns credit and what does not, often with the very distinctions students agonize over. A student who reads the guidelines before designing can aim at targets instead of rumors. A student who reads them again before the final review can audit the submission row by row, asking of each requirement where its evidence lives. Teachers hold copies, the College Board publishes them with the course materials, and the hour spent with them returns more score per minute than almost any other activity in the window.

Weight is the question students ask most and the one this guide answers with deliberate care. The Create Task is one of the course's scored components alongside the end-of-course exam, and its share of the final AP score is set by the College Board in the course framework, where the exact figure in force for a given year is published. That share is substantial enough that teachers schedule a significant block of class time for the work, and students should confirm the figure in the framework for their own year rather than rely on any summary. What no version of the framework has ever suggested is that the task is minor: performance within it moves final scores, and the students who treat it as a major assessment from the first session are reading the situation correctly.

## Failure Patterns Worth Naming

The planning section promised that mistakes recur in recognizable shapes, and a field guide to those shapes lets a student diagnose trouble while it is still cheap. The first pattern is the hollow core: a program with an attractive surface and no center, where the list decorates rather than works, the featured procedure wraps a trivial job, and the algorithm's branch resolves the same way on every input. Hollow cores arise when students design for appearance, asking what the program will look like before asking what it will compute. The cure is the design sketch discipline, because a sketch that names the computation exposes hollowness while the program is still a paragraph.

The second pattern is the afterthought writeup, examined earlier from the scoring side and worth naming here as a schedule failure rather than a writing failure. Students who produce thin responses almost never lacked the ability to explain their programs; they lacked the sessions, because building consumed the window and explanation inherited the scraps. The journal habit and the response drafts seeded during design exist precisely to break this pattern. Explanation begun early also feeds back into design, since a student who cannot yet explain a planned feature usually does not yet understand it well enough to build it.

The third pattern is contradiction drift, the slow divergence of the three artifacts as the code evolves. The response describes the algorithm as it was designed in the second week; the code implements the algorithm as revised in the fourth; the video, recorded from an intermediate version, shows behavior matching neither. No single artifact is dishonest, yet together they testify against one another. Version discipline plus a freeze before recording and final writing is the entire cure, and it costs nothing but the willingness to declare the program done.

The fourth pattern is borrowed weight: a submission whose load bearing parts the student cannot explain, because a tutorial, a classmate, or a generated snippet supplied them. This pattern sometimes survives weak review and always fails the student's own interest, since the course's credit is meant to certify the student's understanding. It also tends to unravel practically: borrowed code resists modification, so the first scope cut or bug fix that touches it stalls the whole schedule. Designing within one's own fluency is not a limitation on ambition; it is what makes ambition finishable inside a fixed window.

The fifth pattern is the demonstration gap, where the video shows a program quite different from the one the responses celebrate. Perhaps the featured algorithm never fires on the demonstrated path, or the list's processing happens offstage while the recording shows menus opening and closing. Readers score the evidence presented, and a gap between the celebrated features and the shown behavior wastes the strongest material the student built. Aligning the demonstration path with the featured structures, rehearsing inputs that exercise the branch and the loop, closes the gap with an hour of planning rather than a rebuild.

## Designing for the Reader

Every artifact in the submission is ultimately read by a person working through many submissions, and design that respects that reader earns its keep. The reader's experience begins with orientation: within the first minute, they should know the program's purpose, recognize its main structures, and feel the submission's organization working in their favor. Students control that experience more than they realize. A purpose stated crisply in the first response, code whose key structures are commented at their creation points, and a video that reaches the program's real behavior quickly all tell the reader that this submission knows what it is about.

Signposting is the craft of making structure findable. In the code, signposts are the comments and names that announce the list, the procedure, and the algorithm where they live. In the responses, signposts are the sentences that name the exact structure being discussed before analyzing it, so the reader never wonders which list or which procedure is under discussion. In the video, signposts are the moments where the demonstration pauses on the output that matters and lets it be read. None of this is decoration. Scoring is an act of locating evidence, and every signpost shortens the distance between a requirement and its proof.

Consistency across the submission functions as a signpost of its own. When the responses use the same names for structures that the code uses, when the video demonstrates the inputs the responses analyze, when the purpose in the first response matches the behavior in the recording, the reader's confidence compounds. Inconsistency spends that confidence. A submission whose parts were plainly built in conversation with one another reads as the work of a single designing mind, which is precisely the impression the task exists to create and certify.

There is a temptation, when designing for a reader, to perform understanding rather than to display it: inflated vocabulary, grand claims about the program's sophistication, responses that gesture at depth. Experienced readers discount performance quickly, because performance lacks the fingerprints of real work, the specific values, the named boundary case, the admitted tradeoff. Display, by contrast, is quiet: here is the list, here is what travels through it, here is the pass where the algorithm surprised its author and got fixed. Students should aim for the submission that sounds like a builder reporting on a build, since that is the voice the guidelines were written to reward.

## When the Plan Meets the Code: Mid-Window Revisions

No plan survives contact with an actual build unchanged, and the Create Task is no exception. The professional skill on display in the middle sessions is not fidelity to the first sketch; it is revision with judgment. A list designed to hold single values may reveal, once real data arrives, that pairs would serve better. A procedure imagined as one job may split into two when its second caller needs only half of it. An algorithm sketched elegantly may prove, under testing, to carry a boundary case it handles badly. Each discovery is the process working, provided the student revises the design deliberately and updates the journal and the response drafts to match.

Refactoring is the disciplined form of that revision: restructuring working code without changing its behavior, so that its organization catches up with what the author has learned. Extracting a repeated block into a procedure, renaming variables whose meanings have sharpened, reorganizing the list's representation, these are refactorings, and the window's middle is their natural home. The safety rule is to refactor in small steps with tests between them, keeping a saved version that works before each change. A student who follows that rule can improve the design fearlessly; a student who rewrites in sweeping gestures trades a working program for a hypothesis.

Cutting is the other mid-window discipline, and it deserves the same respect as building. Every feature carries a cost in sessions, in testing, and in explanation, and the features worth cutting announce themselves: they serve no requirement, they resist completion, or their explanation would be thinner than the structures already present. Cutting early returns sessions to the core. Cutting late merely amputates. The decision rule from the planning section applies unchanged: the load bearing structures are untouchable, the decorations are negotiable, and a smaller program that fulfills its purpose with clarity beats a larger one that gestures at five purposes and fulfills none completely.

Recovery from a lost or wasted session belongs in the same conversation, because it happens to nearly everyone. A session dissolves into an environment problem, a misconception pursued for an hour, a bug that turns out to be a typo. The plan absorbs the loss if the schedule held buffer and if the journal records where the work actually stands. What a student must not do is repay the loss by borrowing time from the recording and writing sessions at the end, which converts one bad session into a weak submission. The funnel shape of the walkthrough exists to protect the close; honoring it under pressure is the mid-window's hardest and most valuable decision.

Revision also has a social dimension worth handling cleanly. Teachers can advise on whether a revised design still addresses the requirements, and that advice is most useful when sought at the moment of revision rather than after the rebuild. Classmates can share war stories about similar bugs. The authorship boundary does not move during revision: the new design, like the first one, must be the student's own, explainable in the student's own words. A revision the student cannot explain is not a revision but a replacement, and replacements are what the originality rules exist to prevent.

## The Rules of the Road: Help, Collaboration, and Original Work

The Create Task measures an individual student's understanding, so its rules protect individual authorship while still allowing the ordinary help that learning involves. Understanding those rules precisely matters, because both directions of error are costly. A student who accepts help beyond the boundaries risks the validity of the whole submission. A student who refuses all help out of an exaggerated caution wastes legitimate resources the guidelines intend them to use, including the teacher standing in the room.

Permitted help shares a common character: it improves the student's own work without becoming the student's work. A teacher may explain a concept from the course, clarify what a requirement asks, demonstrate a technique on an unrelated example, or help untangle the environment's settings. A classmate may discuss how loops behave, how a list might be organized in the abstract, or how they are thinking about their own quite different program. In each case the student still makes the design decisions, writes the code, and composes the explanations. The help informs the hand; it does not replace it.

Prohibited help is equally recognizable once named. Another person, whether classmate, tutor, sibling, or stranger on a forum, must not design the program's structure, write or substantially revise its code, or draft the written responses. Code taken wholesale from a source and presented as the core of the submission fails the same boundary, credit or no credit, because the responses would be claiming understanding the author never exercised. The guidelines also expect the work to be developed during the designated class window under the teacher's administration, which is another reason the version trail and session journal matter: they make authentic development visible.

Judgment calls live between the poles, and students should surface them rather than decide them alone. A teacher's suggestion about which of two student designed approaches better fits the requirements is guidance. A teacher's sketch that becomes the program's architecture is authorship. Asking a forum why a loop condition misbehaves on a small example the student wrote is ordinary debugging culture. Posting the program and asking for the recommendation algorithm is outsourcing the assignment's heart. When a case feels close, asking the teacher before accepting the help is always the safe move, because the teacher administers the task and can rule on its rules with authority.

The principle underneath every specific rule is explainability. At any moment, the student should be able to explain any part of the submission: why the list holds what it holds, why the procedure takes the parameters it takes, why the algorithm branches where it branches, in their own words, without notes, without the original helper present. Work that passes that test is the student's in every sense that matters. Work that fails it is a liability regardless of how it was acquired, because the written responses will expose the gap in the student's own handwriting.

## The Create Task Among Your Wider AP Commitments

Few students take AP Computer Science Principles in isolation, and the Create Task window often overlaps with deadlines and examinations in other subjects. The planning habits this task demands, scope control, session sized goals, protected verification time, transfer surprisingly well to the rest of an AP program, and students who run several courses at once learn to treat their calendar the way this guide treats the window: as a fixed resource allocated deliberately rather than as weather that happens to them. The series' [complete guide to AP exams](/2008/11/08/ap-exams-complete-guide/) surveys that wider landscape for students balancing several subjects in a single season.

Perspective helps when the window feels heavy. This task is one component of one course, and its demands, while real, are bounded and published in advance, which makes it among the most manageable obligations in a crowded season. The students who fare best are rarely those who grant it unlimited hours; they are the ones who give it its scheduled sessions with full attention, use the intervals for other work without guilt, and let the plan, rather than anxiety, decide when the program gets another hour.

There is also a sequencing insight hiding in the calendar. The Create Task rewards work spread across its window, which makes it a poor candidate for the heroic weekend that rescues other assignments. Students carrying several AP courses learn to distinguish the obligations that compress well, a review sheet, a problem set, a reading, from the ones that compress badly, and to protect the uncompressible ones with early starts and steady sessions. Recognizing which kind of obligation one is facing, in any subject, is a study skill with a long half life.

The exam that completes this course deserves a place in the same plan. The end-of-course examination draws on the concepts the task exercises, data, algorithms, programming, and computing's effects on people and society, and it arrives on the national schedule regardless of how any individual window was spent. Students who keep light contact with the broader course during the project weeks, a review session here, a practice set there, reach the examination without a cold start. The project and the examination are partners in the course's design, and treating them as rivals for the same hours misunderstands both.

## The Final Review

The final review is an audit, not a celebration, and it should be conducted with the checklist open and the three artifacts side by side. Begin with the program: run it fresh, follow the demonstrated path exactly, then wander off that path deliberately and confirm nothing collapses. Confirm the version about to be submitted is the version tested, recorded, and described, and that no stray experimental copy is the one packaged. Many submissions have been weakened not by weak work but by weak filing, the polished draft left in the wrong folder while an ancestor went out under the student's name.

Turn next to the video with a stranger's eyes. Watch it once, without pausing, and note every moment where a viewer unfamiliar with the program would hesitate: an input whose purpose is unclear, an output that arrives without being connected to its cause, a pause that reads as malfunction. If the recording can still be remade inside the window, remake the flawed portions. If it cannot, consider whether the written responses can shoulder more of the explanatory load for the moments the video leaves ambiguous, since the artifacts are scored together and can support one another.

Then read the responses as a reader would, pen in hand, checking each claim against the code it cites. Does the purpose statement match what the program observably does? Does the list explanation name the real collection and describe processing the code genuinely performs? Does the procedure explanation describe the actual parameters and the actual callers? Does the algorithm explanation trace steps the code truly executes, with the branch and loop where the answer says they are? Every mismatch found in this pass is a point defended; mismatches left standing are points donated.

Close the review with the administrative layer. Credits for adapted code are present and precise. The files are the ones the process expects, named and stored as the teacher directs. The submission has been checked against the guidelines in force for the year one final time, requirement by requirement. And the student can explain, standing on one foot if necessary, every load bearing decision in the program. A review that ends there has done its work, and the student can let the submission go with the particular calm of someone who has verified rather than hoped.

### What does a calm final session look like?

Nothing new gets built. The student runs the submitted version once more, plays the video start to finish, rereads each response beside the code it describes, and confirms the credits. Discoveries are limited to small mismatches that small edits can repair. Calm is the sound of verification replacing hope.

## What the Task Leaves Behind

A submission, once sent, stops changing, but the habits built while producing it keep working for the student. The most portable of them is decomposition: the reflex of breaking a problem into named parts with clear jobs, which serves in every later programming course, in science projects that involve data, and in any work where a large deliverable must be planned against a fixed date. Students often report that the Create Task was the first school assignment where the plan itself felt like part of the grade, because the window made planning visible. That lesson generalizes far beyond computer science.

Explanation is the second inheritance. Writing the responses teaches a specific and underrated skill: describing a technical artifact accurately to a reader who cannot ask questions. Engineers write such descriptions constantly, in documentation, in design reviews, in commit messages and incident reports, and the student who has practiced tying every claim to inspectable code owns a head start in all of them. The discipline of the substitution test, rewriting any sentence that could describe anyone's work until it describes only one's own, is worth carrying into every subject that asks for analysis rather than summary.

The task also leaves behind a working program the student genuinely owns, designed, built, tested, filmed, and defended in prose. As a portfolio piece it differs from classroom exercises in exactly the ways that matter to a reader: it was chosen rather than assigned in its particulars, it survived contact with real debugging, and its author can discuss its tradeoffs intelligently. Students heading toward further study in computing, including the Java centered work of AP Computer Science A or the data reasoning of AP Statistics, carry both the artifact and the fluency it represents.

Finally, the task leaves a calibrated sense of scope. Having once watched an over ambitious design meet a fixed window, a student sizes the next project differently: smaller core, earlier testing, explanation drafted alongside construction, verification protected at the end. That calibration is the quiet thesis of this entire guide. The Create Task rewards a clear abstraction and an algorithm the student can explain, planned early enough that the writeup becomes easy. A student who internalizes that sentence has learned the course's most transferable lesson, and the score tends to follow the learning.

## Rehearsing the Explanation: A Self Interrogation

Before the written responses are finalized, a student can interrogate the submission the way a reader will, using questions sharp enough to expose soft spots. Start with the list. What does one element represent, exactly, and where in the code is that representation created? Which stretches of code read the collection, which change it, and what would each of them do if the collection were empty or ten times larger? If any answer requires searching the code with uncertainty, the response about the list will inherit that uncertainty, and the time to remove it is during rehearsal, not during composition.

Turn the same light on the procedure. Who calls it, with what arguments, and what would each caller lose if the procedure vanished and its body had to be copied into place? What does the procedure assume about the program's state when it begins, and what does it guarantee when it ends? A student who can answer those questions crisply owns the procedural abstraction in the only sense that matters. A student who cannot has located the precise paragraph of study the next session should begin with, which is a gift disguised as discomfort.

The algorithm submits to a different test: narration under pressure. Describe the computation aloud, start to finish, without looking at the code, then check the narration against the code line by line. Every place the narration skipped a step, the code contains a step the student does not fully own. Every place the narration invented a step, the response was about to claim something false. Two narrations, one on ordinary data and one on a case built to stress the branch and the loop boundary, constitute a rehearsal thorough enough to write from with confidence.

End the interrogation with the artifacts held against one another. Play the video and read the responses in parallel, pausing wherever the prose describes behavior the screen has not shown or the screen shows behavior the prose never mentions. Open the program and hunt for the exact lines each response cites. The exercise takes less than a session and routinely finds the one contradiction, the stale description, the renamed procedure, that the whole apparatus of planning and journaling existed to prevent. Finding it in rehearsal is the system succeeding one final time.

Rehearsal has a byproduct worth naming: it converts anxiety into inventory. A student who has interrogated the submission knows precisely which explanations are strong, which claims rest on thin code, and which moments in the video carry the argument. Nothing about the scoring becomes mysterious after that, and the remaining sessions can be allocated by evidence rather than by dread. Weak spots discovered early enough can still be strengthened in the code; weak spots discovered too late can at least be described honestly, and honest description of a modest structure outscores confident description of an imaginary one every time a reader compares prose against program.

The interrogation also scales down gracefully for students whose windows have gone sideways. Even a single pass through the questions, list, procedure, algorithm, artifacts, performed in one sitting with the code open, catches the failures most likely to cost credit: the response describing a feature that was cut, the video demonstrating a version that no longer exists, the list explained as central while the code touches it once. Perfection is not the standard the scoring applies; coherence is, and coherence is exactly what one honest rehearsal audits.

Students sometimes ask when rehearsal should begin, and the honest answer is that the habit pays from the moment the working core first runs. A five minute narration after each successful test, what changed, what the algorithm did with the new input, why the branch fired, builds the explanatory muscle gradually instead of demanding it all in the writing sessions. By the time the responses are drafted in earnest, the student has already told the program's story dozens of times in miniature, and the written versions arrive as transcriptions of practiced explanations rather than as inventions under deadline pressure. Fluency of that kind cannot be faked, and readers, who spend their days distinguishing fluency from performance, recognize it on contact.

## Frequently Asked Questions

### Q: What is the Create Task on AP Computer Science Principles?

It is the performance task at the heart of AP Computer Science Principles, in which each student designs and builds an original program during designated class time, records a short video of the program running, and writes responses explaining the program's design. The program must accept input, produce output, and serve a purpose the student chooses. Inside the code, three structures carry the task: a list that stores data as a collection, a procedure the student developed that performs a defined job, and an algorithm that combines sequencing, selection, and iteration. The submission is scored against College Board guidelines, and the work must be the student's own, developed inside the administered window. Students meet the task as one of the course's scored components, introduced and administered by their teacher, so the shape of the work is published and knowable long before the first session begins.

### Q: How is the Create Task scored on AP Computer Science Principles?

Trained readers apply the College Board's scoring guidelines to the whole submission: the program, the video of it running, and the written responses. Credit attaches to demonstrated evidence, requirement by requirement. Readers look for a program with a clear purpose that takes input and produces output, a list that stores data so the purpose can be achieved, a student developed procedure that contributes to the program's function, and an algorithm where sequencing, selection, and iteration combine. The written responses are where the student identifies and explains each structure, so explanation quality influences the outcome heavily. Partial evidence earns partial standing, and claims the code contradicts earn none. Because readers see code, recording, and prose together, consistency across the three artifacts quietly supports every individual judgment they make about where credit belongs.

### Q: What do you submit for the Create Task on AP Computer Science Principles?

Three artifacts make up the submission. First comes the program itself, the complete code of the application the student built, in whatever language or environment the student used. Second comes a video that shows the program running, with input being supplied and the resulting output visible, so a viewer can confirm the program behaves as described. Third come the written responses, in which the student states the program's purpose and function and explains the list, the procedure, and the algorithm inside the code. The three pieces are scored together, and they should agree with one another in every detail a reader might compare. Submitting material beyond what the process requests adds no advantage, while leaving out any one of the three pieces leaves whole requirements with no evidence for a reader to attach credit to.

### Q: How much time do you get for the Create Task on AP Computer Science Principles?

The work happens inside a set window of designated class time that the teacher administers under College Board rules, spread across multiple sessions rather than completed in one sitting. The College Board publishes the framework for that window, including the minimum class time schools must provide, in the guidelines in force for the year, and students should confirm the specifics there and with their teacher, since the documents can change. What the structure means practically is that the schedule is fixed and known in advance: design, building, testing, recording, and writing must all fit inside it, which is why planning and scope control matter so much. Teachers communicate the session schedule for their own classes, and a student who maps personal milestones onto that schedule early rarely faces a surprise when the window closes.

### Q: What is the program requirement for the Create Task on AP Computer Science Principles?

The program must be a working piece of software the student developed for the task, written in a language or environment of the student's choosing. It must accept input, from a user, a file, or another source the environment supports, and input must genuinely affect what the program does. It must produce output a viewer can perceive, such as displayed results, an updated screen, or a generated artifact. It must serve a purpose the student can state plainly. And it must contain the structures the rest of the submission explains: a list holding a data collection, a procedure the student wrote, and an algorithm combining sequencing, selection, and iteration in service of that purpose. Meeting the letter of the requirement is only the beginning, since readers also weigh how centrally those required parts sit inside the work the program actually performs.

### Q: What is the written response for the Create Task on AP Computer Science Principles?

The written responses are the student's explanation of the submitted program, written in the student's own words as part of the task. Across the responses, the student describes the program's purpose and how its function achieves that purpose, identifies the list in the code and explains how that data abstraction helps manage the program's complexity, identifies a procedure the student developed and explains its contribution as a procedural abstraction, and explains the featured algorithm, showing how sequencing, selection, and iteration work together inside it. Every answer should point at the actual code, naming the real structures and values, because readers score the explanation against the program itself. Responses drafted alongside the code, then revised against the frozen final version, tend to carry a specificity that explanations reconstructed from memory cannot match.

### Q: How do you choose a Create Task project on AP Computer Science Principles?

Choose against four tests. Interest comes first, because the project must sustain effort across many sessions, and a topic the student knows and cares about also makes faulty behavior easier to spot. Scope comes second: the program's core should be describable in a short paragraph, with decorative features that can be cut if the window tightens. ### Q: What is an abstraction in the Create Task on AP Computer Science Principles?

An abstraction hides detail so a program can be understood and built in terms of bigger ideas. The task examines two forms. Data abstraction appears in the list: many values are stored and managed as one collection, so the rest of the program can search, filter, or summarize the whole group without juggling individual variables. In the written responses, the student explains each abstraction and how it helps manage the program's complexity, which is the benefit both forms exist to provide.
